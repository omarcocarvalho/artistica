## A1

PR #155 (`feat(settings): add the preset model and file format`), merge commit: _pending_.

Review summary: `src/shared/model/preset.ts` matches the "Shared contracts → Presets" block and M5-R2, R4 and R5. Every preset is rebuilt field by field from a whitelist (Zod page-setup parse, then portrait custom size and `normalizePageSetup`; a types-only study parse, then `sanitizeStudy`; `sanitizeLines`, then `edges.on`, `face` and `pose` forced off). `parsePresetFile` never throws: it checks the size (UTF-16 length, then UTF-8 bytes) before `JSON.parse`, then `format`, `version` and the migrations table, reads at most 50 presets, each on its own, and counts skipped and adjusted presets. No DOM, no network, no new dependency. The output is deterministic (fixed key order, 2-space JSON, final newline). Reviewer's mutation sample: 18 mutants, 16 killed by the PR's tests. The 2 survivors were fixed with new tests (commit "test(settings): pin adjusted counts …"):
- `sameValues` ignoring arrays survived: a preset whose study versions are reordered or repeated was not proven to count as adjusted. Test added.
- The `presetFromSettings` guard for fields that are not objects was unobserved. Test added (`null`, an array and a string give the defaults).
- The `__proto__` test's nested case was a no-op (`JSON.stringify({ ...o, __proto__: null })` writes no `__proto__` key). It now writes own `__proto__` keys into `pageSetup`, `study`, `lines` and `lines.grid`, and checks that none of the output objects has one and that each keeps `Object.prototype`. A mutant that copies an own `__proto__` key into the output is killed.

Killed mutants in the sample include a recursive merge that pollutes `Object.prototype`, raw keys spread into the page setup, study or lines, `>=` for the newer-version and UTF-8 size checks, the edge detail reset, `pose` not forced off, skipped counted without the cap, no name normalisation in `presetFromSettings`, no portrait custom size, no `empty` check, and `buildPresetFile` without the whitelist.

- Ruling (controller, A1): A1 keeps its own copy of the page-setup Zod schema to avoid an import cycle with `features/settings`. Accepted for A1. **Binding for A2:** leave only one copy, either by importing it from `preset.ts` or by moving it to `src/shared/model/` and importing it from both. The "same sanitizers as saved settings" property keeps the two copies equal until then. Recorded in the overview under "Contract change requests → Ruled".
- Ruling (controller, A1): on import, a preset whose name is empty, not a string or longer than 40 code points after normalising is skipped and counted in `skipped`. It is not truncated. Accepted as the default (Q13 below).
- Ruling (controller, A1): no JSON reviver and no Zod schema for lines. Accepted: every object is rebuilt from the whitelist, `sanitizeLines` is total (M3-R16), and the strengthened prototype-pollution test stands.
- Ruling (reviewer, A1): `presetFromSettings` keeps a name that `presetName` refuses as given, so A2's `savePreset` can return `'bad-name'`. `buildPresetFile` drops such a preset. Recorded in the overview's Ruled entry.
- Deferred (reviewer, A1, for A3): `presetName` accepts a name made only of characters that `\s` doesn't match and that render as nothing (e.g. U+200B, control characters). A3 shows names as plain text, so this is cosmetic. A3 may refuse them in the dialog.

## C1

PR #158 (`fix(ui): move segmented controls with all four arrows, Home and End`), squash-merged to master; the merge commit is the one with that title. Reviewed independently.

- **Review:** the control follows M5-R26. Radix keeps the focus movement and the roving tabindex. The control selects on key down for all four arrows, Home and End: the next enabled option from the focused one, wrapping, with Left and Right swapped in RTL. All five usage sites have a test. The checked option drops its accent underline in forced colours (M2 deferred item), checked by a CSS-source unit test and a computed-style E2E assertion. No privacy, determinism, dependency or UI-string impact.
- **Reviewer fixes:**
  - The direction was read only on focus, so in an RTL page the control was drawn left to right until first focused (Radix writes `dir="ltr"` on its root). It is now read on mount as well (`useLayoutEffect`), and a test covers it.
  - Radix also moves focus on Page Up and Page Down, without selecting, which left the focus on an unchecked option. Those keys now select the first and last enabled option, like Home and End, and a test covers each.
  - Two tests added for mutations that survived: a direction change after mount, read on focus, and stepping from the focused option when the value does not follow.
- **Mutations (reviewer):** without the mount-time read, 1 failed; without the read on focus, 1; without Page Up, 1; without Page Down, 1; with `orientation="horizontal"`, 9; with Up and Down swapped in RTL, 2; no wrapping, 8; direction read from the group itself, 4; stepping from the value, not the focused option, 1 (it survived before the new test); without the forced-colours `box-shadow: none`, the CSS test failed.
- **Checks:** lint, format:check, typecheck, test:coverage (2576 passed), test:perf (16), build. E2E keyboard, forced colours and L-D6 passed on chromium, firefox and webkit. A local webkit failure was the browser process being killed (`SIGKILL`) on a host under heavy load, after the corner step. It passed on reruns.
- Ruling C1-1: the selection-on-key-down hybrid is accepted. Radix's arrow selection depends on the key still being down when its focus timer runs, which a quick tap misses in chromium. That is why the `{ delay: 50 }` workaround in L-D6 existed, and it is removed.
- Ruling C1-2: the forced-colours check is a CSS-source unit test plus a computed `boxShadow === 'none'` assertion in the chromium forced-colours E2E. It is not a computed-style test in `forms.test.tsx`, because happy-dom neither loads the CSS nor evaluates `forced-colors`. Accepted.
- Ruling C1-3: the extra files (`e2e/a11y.spec.ts`, `e2e/support/targets.ts`, `e2e/lines.spec.ts`, the three usage-site tests) are in scope. They are the plan's step 3 checks and the E2E proof. Port 4703 instead of 6701 is accepted (dispatch instruction).
- Ruling C1-4: the group drops `aria-orientation` because it responds to both axes. Accepted.
- No contract change, no new question.

## D5

PR #162 (`perf(images): decode large photos straight to their downscaled size`), merge commit: _pending_.

Review summary: `decodeResized` in `src/features/images/decode.ts` makes one `createImageBitmap(blob, { imageOrientation: 'from-image', resizeWidth, resizeHeight, resizeQuality: 'high' })` call at the upright target. The target is the preview size on import and the `planDownscale` size on export. The upright size comes from the header (SOF or IHDR, with an EXIF 5–8 swap). The path runs only when the header gives a usable size, the target is smaller, `resizeOnDecode()` is true, and the photo is orientation 1 or the browser applies EXIF itself. Otherwise the two-step path runs unchanged. `resizeOnDecode` is true only in WebKit (user-agent gate) and only after a cached 4×2 → 2×1 probe. In Chromium and Firefox the decode calls are unchanged. The export still decodes from the kept compressed source to `pxW × pxH`, so import and export agree on the size. The page model, both renderers and the layout inputs are unchanged, and the layout stays deterministic (the header size equals the decoded size for a valid file). Privacy: no new network path, nothing is stored, no new dependency.

Reviewer's re-run of the spike (local macOS arm64, Playwright 1.63, synthetic noisy JPEGs). Each run uses a fresh browser. The figure is the peak RSS increase of every `ms-playwright/<engine>` process during one decode, sampled every 25 ms, as two-step / resize:
- WebKit, 5 runs, median: 12 MP → 2048 preview 162 / 29 MB (85–169 / 27–31), 79 ms instead of 135 ms. 50 MP → 5016×3344: 635 / 554 MB, bimodal (resize 195–616, two-step 433–654), 338 ms instead of 614 ms. 100 MP → 5016×3344: 1031 / 818 MB, 692 ms instead of 1163 ms.
- Chromium, 3 runs, median: 50 MP 308 / 501 MB, 100 MP 650 / 553 MB, about the same time. Firefox: 50 MP 277 / 276 MB, 100 MP 424 / 488 MB, the resize path slower. Neither engine has a reliably lower peak, which supports leaving them unchanged.
- WebKit's gain at 50 MP is smaller and noisier than the PR's table (697 / 179). It is consistent at 12 MP, the spec's case. In every WebKit case the minimum and the median are lower and the decode time about halves.
- Pixels, resize against two-step, mean absolute difference per channel: WebKit 2.89, 2.54, 2.95 on per-pixel noise (max 30), 0.01–0.04 on smooth content and on a 50 MP PNG. Firefox is similar (2.6 on noise). Chromium is identical. The EXIF-6 file gives the same difference as the upright file at 3344×5016 in all three engines, so the browser rotates before it resizes.
- In-app check (temporary spec, not committed): a 6000×4000 quadrant JPEG with EXIF 6. In WebKit the app probed once, imported with `resizeWidth 1365, resizeHeight 2048`, showed the photo upright as 4000 × 6000, and exported with `3344×5016`. Chromium and Firefox made the same calls as on master.

Findings fixed on the branch (commit "test(images): keep the two-step decode for a zero-sided header …"):
- A JPEG whose SOF declares height 0 (the height comes later in a DNL marker) would have been resized to `w × 1` and reported as such, because the resize path trusts the header. `decodeResized` now needs both sides ≥ 1. Test added, and the mutation that removes the guard is killed.
- Surviving mutant: the probe checking only the width. Test added (a 2×2 result counts as not honoured).

Reviewer's mutation sample (13 mutants, all killed after the fixes): no upright swap; the EXIF gate even for orientation 1; no EXIF gate; `resizeQuality` dropped; `imageOrientation: 'none'` on the resize; export at the preview size; import reports the resized size as the original; resizing at equal size; no probe caching; the UA gate letting Chrome in; the UA gate letting Firefox in; the probe checking only the width (killed after the fix); no zero-side guard (killed after the fix).

Checks: lint, format:check, typecheck, test:coverage, test:perf and build all pass. E2E (port 4810): `import`, `studies-imports`, `layout-export` and `privacy` on chromium and webkit (57 passed, 27 skipped by project), and `mobile-flow` on mobile-webkit (15 passed, 2 skipped).

- Ruling (reviewer, D5): the plan's "M1 decode tolerance" does not exist. The bar for D5 is a mean absolute difference per channel of at most 3/255 against the two-step path on per-pixel noise (the worst case, within the spread the two-step path already has across engines), at most 0.5 on smooth content, and the same upright size and orientation. WebKit meets it, so the change applies to WebKit.
- Ruling (reviewer, D5): accepted that a user-agent gate (WebKit, not Chrome, Chromium or Edg) sits on top of the feature probe. A feature probe can't tell a decode at the smaller size from a full decode scaled afterwards, and Step 3 says nothing changes for engines without a lower peak. A WebKit browser whose `createImageBitmap` ignores the options fails the probe and keeps the two-step path.
- Ruling (reviewer, D5): on import, "the plan downscales" means the preview target (`previewSize(planDownscale(...))`), because import keeps only the preview. On export, the resize path runs only when `planDownscale` shrinks the photo.
- Ruling (reviewer, D5): accepted that the resize path takes `originalPxW/H` and `pxW/H` from the header. Import and export both use the header, so they always agree. The zero-side guard covers the one known case where a header disagrees with its pixels.
- Ruling (reviewer, D5): no lasting E2E for the WebKit resize path in D5. The temporary spec above checked it, and M5c (D7) measures large photos on CI. D7 may add an EXIF-6 large-JPEG import on webkit if it wants a lasting guard.
- Ruling (reviewer, D5): `DecodeDeps.resizeOnDecode` is an internal interface (only `browser-deps.ts` and the tests implement it), so it isn't a contract change.
