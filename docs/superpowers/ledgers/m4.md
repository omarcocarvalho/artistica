## Rulings

- **Ruling (A1, persistence):** until D1 (settings v4), the settings envelope writes `lineDefaults.edges`, `face` and `pose`, and the v3 schema strips them on load. Accepted instead of filtering them out in `partialize`. The guide switches written are always `false` (both `setLineDefaults` and load go through `normalizeLineDefaults` = `withoutLineTypes(sanitizeLines(…))`), so owner Q8 holds: switches are never remembered. No UI can change the detail before E1 and nothing deploys between A1 and D1 (deploys only on release), so the stored detail is the default 50. D1's own schema stores the same keys. A filter would be code that D1 deletes. E2E P2 pins the envelope. Nothing derived from a photo is involved.
- **Ruling (A1):** `NO_GUIDES` is `null` for every kind ("nothing known"), never an empty result (`[]` or `{ polylines: [] }` would mean "searched and found nothing", which drives the "No face found" note). Pinned in `guides/types.test.ts`.
- **Ruling (A2, rotation table):** `sourceToFrame` and `fromRotated` call the exported `orientMatrix` instead of importing the module-private `ROTATION_COEFFS`. Accepted: `orientMatrix` is the only reader of the table and is what the tiles print with, so the table is still not duplicated and the guides cannot drift from the pixels. The hand-written 16-case corner table kills a mutant of any table row.
- **Ruling (A2, `PxRect`):** `meetsCrop` takes `PxRect` (`render/pixels/tile-plan.ts`); the overview's `RectPx` never existed. The overview's contract text is corrected (Contract change requests → Ruled).
- **Ruling (A2, `fromRotated` oracle):** tested against a 3 × 2 grid turned clockwise by hand, plus a property against `orientMatrix`'s normalised rotation, instead of `rotateBitmap`, which does not exist yet. Accepted.
- **Ruling (A2, import cycle):** `guides/map.ts` imported `resolveCrop` from `build-page-models.ts`, which imports `tile-lines.ts`; once D3 makes `tile-lines.ts` import `guides/map.ts` the modules would form a cycle. Prevented now: `resolveCrop` (and its tests) moved unchanged to `src/features/render/crop.ts` (`crop.test.ts`), a leaf module with type-only imports, and `build-page-models.ts` and `map.ts` import it from there.
- **Ruling (A2, touching boxes):** `meetsCrop` is a closed test, so a box that only touches the crop's edge, and a zero-width or zero-height box (a straight vertical or horizontal edge chain), counts as meeting it. Accepted: culling only saves work, the tile clip (= trim, M3-R4) trims whatever is kept, so a kept touching polyline draws nothing and costs at most its vertices.
- **Ruling (D1):** `migrate` stays `parseSettings`, though `merge` also runs `parseSettings` on every load, so it is redundant for correctness. It keeps a migrated envelope valid on its own if `merge` changes. The mutant that makes `migrate` the identity survives for that reason and is recorded as equivalent.
- **Ruling (D1):** the inner `.catch` on `edges.detailPct` stays although it is an equivalent mutant (the outer `edges` fallback gives the same result, since `on` is always forced off). It matches the field-by-field pattern of the other nested groups.
- **Ruling (B1-R1, controller):** Detail must be monotonic ("the outline gets denser as Detail goes up", owner sign-off). `edgeParams` returns `blurPasses = EDGE_BLUR_PASSES = 2` at every detail; only `keepShare` and `minChainPx` vary. With the blur fixed, a higher `keepShare` only lowers both thresholds over the same NMS survivors, so the edge map at d + 1 contains the one at d. Chosen from edge maps of real photos at blur 0–3 × detail 1, 25, 50, 75, 100: 0 and 1 turn feathers and fur into hatching from mid detail up, 3 drops inner shapes at low detail, 2 gives the main shapes at 50 and still gets denser up to 100. B2's "never fewer chains" property is replaced by coverage (chains can join or split as pixels are added).
- **Ruling (B1-R2, controller):** `high ≥ MIN_STRONG_MAG2 = 32²`, so a linear gradient never seeds an edge.
- **Ruling (B1-R3, controller):** NMS keeps a pixel ≥ the neighbour ahead along the gradient and > the one behind; outside the image counts as 0.
- **Ruling (B1-R4, controller):** one blur pass is the exact 2D integer sum divided once (`>> 8`, truncating).
- **Ruling (B1-R5, controller):** `high` is taken from the sorted survivors, not a histogram (same value). The sort is not too slow: about 4 ms at 1024 × 768 and 15 ms at 2048 × 1536.
- **Ruling (B1-R6, controller):** `edgeParams(NaN)` is detail 50.
- **Owner decision (C1, 2026-10-08):** skip the iPhone spike; the iPhone is checked at M4 sign-off instead (speed, memory, the worker, offline). The Execution owner gate is resolved; C2 and C4 may proceed.
- **Owner decision (C1, 2026-10-08), M4-R5a:** load one landmarker at a time, never face and pose together, so the guides phase stays under 1500 MB (1437–1461 MB one at a time vs 1526–1545 MB with both, CI mobile-chromium). Binding for C4: one engine instance loaded at a time; switching from face to pose closes the first, then loads the second; the FIFO serialises. The 1500 MB budget is unchanged. E4's memory test expects about 1437–1493 MB (with the edge worker) and asserts face and pose are never loaded together.

- **Ruling (B2-R2, reviewer):** the budget is a greedy fill in longest-first order, not a strict prefix: a chain that does not fit is skipped and shorter ones are still tried (overview B2-R2). It matches M4-R16's intent, a dense outline within the budget, and stays deterministic.
- **Ruling (B2, "longest"):** a chain's length is its pixel count before simplification (a closed chain counts its repeated start once), ties by the first point's scan index. Integer and independent of RDP, so the order is fixed before any simplification; recorded in M4-R16.

## Notes for later tasks

- **E1/E2, the "N on" badge:** `LinesSection` counts `activeLineTypes(img.lines).length`, which includes guide types from A1. No UI can turn a guide on before E1. The overview's E2 wiring says the badge counts guide types, so the behaviour is intended; E1/E2 confirm it with a test (a guide switched on raises the count).
- **C2–C4, coverage:** the existing `src/features/lines/**` glob in `vite.config.ts` covers every future `src/features/lines/detect/*` module (loader, worker wrappers, engines), not only `detect/store.ts` and `detect/schedule.ts`, so they fall under the 80% gate. Exclude worker and loader shells explicitly (as the M2/M3 workers are) or test them to 80%.
- **E2 (binding, from D2), `fromRotated` against the real bitmap:** D2 does not build `bitmapFor`, so the test moves to E2: once `bitmapFor` (the rotated preview bitmap, M4-R7) exists, E2 must test `fromRotated` against it: draw a bitmap with distinct labelled pixels, rotate it with the real code for 90°, 180° and 270°, and check that each label's centre in the rotated bitmap maps back to its source centre. A2's test only pins the clockwise convention of `orientMatrix`.
- **E2 (binding, from D2), edge crop:** E2's `bitmapFor(img, 'edges')` crops the preview with `resolveCrop(img)` (scaled to the preview bitmap), the same resolved crop D2 passes to `fromCrop`, so the detection and the mapping back use one rectangle. Every bitmap is built from the `img` passed in, never from the store's current descriptor.
- **C4 (binding, from D2):** `dispose()` closes the landmarker and terminates its worker before it returns, because the scheduler creates the next engine (the other model) right after it; `prepare` is idempotent per model and is called before every job, restarts the worker after the idle release, and must not transfer (detach) the buffers it is given, which the scheduler sends again.
- **B3, C3, C4 (binding, from D2):** import `EdgeEngine`, `LandmarkEngine`, `AiLoader`, `Progress` from `detect/schedule.ts` and `AiModel` from `detect/store.ts`. `AiAsset` and `AiAssets` are declared by `virtual:ai-assets` (C2); import them from there (`schedule.ts` re-exports them).
- **C3 (from C2), `virtual:ai-assets` in workers:** the `aiAssets()` plugin is in `plugins`, not `worker.plugins`, so a worker cannot import `virtual:ai-assets`; per M4-R3 the worker gets bytes, not the manifest. Under Vitest the base is `/`, so `AI_ASSETS.face.url` is `/models/face_landmarker-float16-1.task` in unit tests and `/artistica/models/…` in builds. The Content-Type GitHub Pages sends for `.task` is still unverified; C3 stores the bytes with its own Content-Type.
