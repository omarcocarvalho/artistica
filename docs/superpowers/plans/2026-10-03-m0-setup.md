# M0 — Setup Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn the empty `omarcocarvalho/artistica` repo into a fully tooled, CI-gated, auto-merging, release-per-milestone project whose placeholder landing page (`/`) and app page (`/app/`) are live at https://omarcocarvalho.github.io/artistica/ as release `v0.0.1`.

**Architecture:** A multi-page Vite 8 build (static landing `index.html` + React app `app/index.html`) served under the base path `/artistica/`. GitHub Actions runs lint, typecheck, unit, E2E (3 browsers + 1 mobile viewport) and build on every PR, plus a PR-title Conventional Commit check; branch protection makes them required, and PRs auto-merge on green. release-please keeps a release PR open; merging it at milestone end creates the release and, in the same workflow run, builds and deploys to GitHub Pages (a separate `workflow_dispatch` workflow allows manual deploys).

**Tech Stack:** Node 24, pnpm 12.8.1, Vite 8.3.2, React 19.3.0, TypeScript 6.0.3 (strict), Tailwind CSS 4.3.3, ESLint 10.12.0 + typescript-eslint 8.71.0, Prettier 3.9.9, Vitest 5.0.3, fast-check 4.10.2, Playwright 1.63.0, @axe-core/playwright 4.13.0, GitHub Actions, release-please, GitHub Pages.

**Spec:** `docs/spec.md` in the repo. Relevant sections: §2.11, §4, §5, §6, §6.1, §7, §8 (M0).

## Review Focus

1. **Assets served under the `/artistica/` subpath.** If `base` is wrong, the pages load as unstyled HTML with 404s for JS/CSS. Expected: no request returns ≥ 400 on either page. Pinned by the "no failed requests" E2E test (Task 2) and the `dist/` path grep in the CI `build` job (Task 3).
2. **The `/app/` entry silently missing from the build.** With multi-page Vite, a missing `rolldownOptions.input` entry means `/app/` 404s on Pages while `/` works. Expected: both pages build and render an `h1`. Pinned by the E2E test running against both pages (Task 2) and the `test -f dist/app/index.html` check (Task 1 Step 9, Task 3 `build` job).
3. **Tailwind not actually applied.** The CSS can load but contain no utilities (for example, a broken plugin or bad source detection). Expected: the `h1` renders at Tailwind's `text-4xl` size (36px), not the preflight-reset 16px or the browser default 32px. Pinned by the `font-size: 36px` E2E assertion (Task 2).
4. **Dark-mode contrast.** The page follows `prefers-color-scheme`, and dark mode could fail colour contrast while light mode passes. Expected: axe passes in both schemes. Pinned by the axe test looping over `light` and `dark` (Task 2).
5. **A PR whose required checks never run, so auto-merge hangs forever.** This covers docs-only PRs (path filters) and the release-please PR (created with `GITHUB_TOKEN`, which does not trigger workflows). Expected: docs PRs get all checks, and the release PR gets checks after the owner closes and reopens it. Pinned by the docs PR and the release PR flow in Task 8, plus the "no path filters" constraint.

Also pinned in Task 8: a PR with a failing check **or** a non-Conventional title cannot merge, even with auto-merge enabled.

/** Document title for a page/section, e.g. pageTitle('App') === 'App · Artistica'. */
export function pageTitle(section?: string): string {

## Git, PRs and releases

- **Never push to `master`.** Every change goes through a PR from a branch.
- **Branch names:** `feat/…`, `fix/…`, `chore/…` (docs, CI, tests and tooling use `chore/…`).
- **Squash merge only.** The **PR title becomes the commit message** and must be a Conventional Commit: `feat:`, `fix:`, `docs:`, `chore:`, `ci:`, `test:`, `build:`, `refactor:`, `perf:`, `style:`, `revert:` (optional scope, e.g. `feat(layout): …`). The `pr-title` check enforces it. The PR body becomes the commit body.
- **Auto-merge:** open every PR with auto-merge on; it merges when all required checks are green, no human approval needed:
  ```bash
  gh pr create --base master --title "feat: …" --body "…"
  gh pr merge --auto --squash
  ```
- **Required checks:** `lint`, `typecheck`, `unit`, `build`, `e2e (chromium)`, `e2e (firefox)`, `e2e (webkit)`, `pr-title`. Never add `paths:` filters to these workflows (a PR whose required checks never run can never merge).
- **Releases: one per milestone.** release-please keeps a release PR (`chore(master): release x.y.z`) open. It is **never auto-merged**. At the end of a milestone, after the owner signs off: close and reopen the release PR (PRs opened by `GITHUB_TOKEN` don't trigger CI; a reopen by a person does), wait for green checks, then `gh pr merge <n> --squash`. Merging creates the GitHub release and deploys to Pages in the same workflow run.
  - Versions: M0 `v0.0.1`, M1 `v0.1.0`, M2 `v0.2.0`, M3 `v0.3.0`, M4 `v0.4.0`, M5 `v0.5.0`, M6 `v1.0.0` (use a `Release-As: 1.0.0` line in the PR body).
- **Deploys:** only on release. Manual deploy for demos: `gh workflow run deploy-pages.yml --ref master`.

## Working agreement: parallel by default, the owner is the only gate

- **Run work in parallel with agents whenever possible.** Whenever two or more pieces of work don't depend on each other (design screens, independent plan tasks, features, test suites, docs, research), send them to agents running in parallel instead of doing them one after another. Each agent gets its own git worktree, branch and PR.
- **The owner's review and decisions are the only gate.**
  - Don't stop to ask permission for routine work that's already in an approved spec or plan.
  - Stop and wait only for:
    1. approving specs, plans and designs
    2. product or scope decisions not covered by the spec
    3. milestone sign-off before a release PR is merged
    4. anything destructive or irreversible
- **Batch questions:** collect them and ask them together, written into the relevant doc (spec or plan), so they don't interrupt the work one by one.
- **Agents never decide product questions themselves.** An agent that hits an open product question reports it back as a question instead of guessing.
