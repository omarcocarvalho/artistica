# M2 — Image studies: Overview & Shared Contracts

> **For agentic workers:** this is the umbrella document for M2. It is **not** executed on its own. M2 is split into four sub-plans (A–D below), each executed with superpowers:subagent-driven-development, exactly like M1. Every sub-plan treats the **Shared contracts** section of this file as binding. A sub-plan that needs a contract change lists it under "Contract change requests" instead of silently diverging.
>
> **Status:** draft for owner review. Nothing in M2 starts until the owner approves this plan and answers (or accepts the defaults of) the **Questions for the owner** at the end.

**Goal:** Ship `v0.2.0`. Each image can print as any combination of four versions — Original, Blurred, Values, Blur + Values — packed together as one group. Blur is 1–100% and scales with the image size; values are 2–20 steps of perceptual lightness mapped onto a single-hue OKLCH ramp. "Apply to all" copies one image's study settings to every image. All pixel work runs in Web Workers: the preview from the in-memory preview bitmap at screen resolution, the PDF from the decoded source at 300 DPI, one image at a time. Value studies are embedded in the PDF as lossless PNG.

**Spec:** `docs/spec.md` §2.4 (study groups), §2.5 (PNG for value studies), §2.6 (image studies), §2.9 (default study settings persisted), §2.12 (phone flow with a Studies step), §3 (non-functional), §4 (architecture), §7 (testing), §8 "M2 — Image studies", Q&A R6, R7, Q24–Q28, design answers D7 ("apply to all" scope), D8 (swatches + hue slider), D9 (ramp L ≈ 0.20 → 0.95). **Design:** `design/studies.html` (desktop Studies tab), `design/mobile-flow.html` (Studies step), `design/workspace.html` / `design/image-edit.html` (the same Studies tab markup), `design/mockup.js` `renderRamps` (ramp prototype), `design/README.md`. **Conventions:** `CLAUDE.md`. **Constraints carried over:** the M1 overview's contracts and rulings (`2026-10-03-m1-overview.md`), the M1 ledgers (`docs/superpowers/ledgers/m1-*.md`) and `HANDOVER.md`.

**M2 exit criteria (spec §8):**

- A sheet showing an image next to its blurred version and its 5-value version prints correctly: three equal tiles side by side in one group on one page, the value tile has exactly 5 tones from the chosen hue ramp and is embedded as PNG, the blurred tile is a JPEG. Proven by E2E (D3, PDF parsed back) and by the owner's real-phone print (sign-off checklist).
- All tests green, on all required checks.
- Unit coverage ≥ 80% on `src/features/layout/**`, `src/features/render/**`, **`src/features/studies/**`** and **`src/shared/colour/**`** (owner decision P3 named studies; components and workers excluded as in M1).
- The M1 memory-budget E2E (M3) passes with studies switched on (22 photos × 3 versions), and the owner's real iPhone export of the exit-criterion sheet and of 20 photos × 3 versions does not crash.

## What M1 left that M2 builds on (read from the code, 2026-10-07)

- **Images** (`src/features/images/`): `LoadedImage` keeps the compressed `source` Blob and a `preview` ImageBitmap of at most `PREVIEW_LONG_SIDE_PX` = 2048 px (PR #75). `decodeFull(image)` decodes the source again at full `pxW × pxH` (capped at 5100 px / 16.7 MP); the caller closes it. `selectImageDescriptors` memoises plain descriptors per `LoadedImage` object.
- **Layout** (`src/features/layout/`): already supports groups. `LayoutItemInput.tiles ≥ 1`; a group is a row (tile aspect ≤ 1) or a column (aspect > 1) with the gutter between tiles; `maxPrintWidthMm` and fixed sizes are per **tile**; a turned row becomes a column with tile *i* i-th from the top, a turned column becomes a row with tile *i* i-th from the **right** (CR-B5). `buildLayoutItems` sets `tiles: 1` today. Keys are `${contentHash}~${occurrence}#${copy}` (PR #66) and the golden snapshot (`golden.test.ts`) pins layouts, including groups of 1–3 tiles.
- **Render** (`src/features/render/`): `buildPageModels` emits one `DrawTile` per placement tile. `planTilePixels(tile, { dpi })` + `renderTile(source, plan, createCanvas)` (crop → step-down resample → rotate/flip → white background → bleed by edge extension) is shared by the preview (main thread, DOM canvas, preview bitmap via `forScaledSource`) and the PDF export (worker, `OffscreenCanvas`). `tileRenderKey` identifies encoded pixels; the composer embeds one image per key. `runExport` decodes **one image at a time** at full resolution, encodes **all** its tiles (on every page), then closes it (`jobsByImage`). `EncodedTileImage.format` already allows `'png'`, and `composePdf` already calls `embedPng` for it.
- **Preview** (`PagePreview`): synchronous; per-page `Map` of rendered tile canvases keyed by `tileRenderKey`, evicting keys no longer on the page (`syncTileCanvasCache`). Redraws only on model/scale/width/guides change (ruling D-3).
- **Shell** (`src/app/`): desktop right panel is `PageSetupPanel` only (no tabs yet); phone steps are `images → page → preview → export`. `createPipeline` debounces 80 ms and calls `layoutAsync` (latest-call-wins) then `buildPageModels`.
- **Settings**: `artistica:settings`, zustand persist `version: 1`, total Zod schema (`.catch` per field), `migrate` = `parseSettings`.
- **Not present yet:** `src/features/studies/`, `src/features/lines/`, any OKLCH/colour maths in `src/shared/` (the spec names it; M2 creates `src/shared/colour/`), the `studies` i18n namespace.
- **E2E**: strict network guard on every spec; `e2e/support/pdf.ts` over `render/pdf/inspect.ts`; `e2e/support/memory.ts` (Chromium RSS sampler); test M3 in `e2e/mobile-flow.spec.ts` (22 × 24 MP, A5, settled < 1500 MB, export peak < 1700 MB).

## Owner decisions that bind M2

From the spec and earlier rounds (already decided — do not re-ask):

- **R6:** versions are per image, any combination, with "apply to all".
- **R7:** the lightest value is always the lightest tint of the chosen hue, never the paper colour.
- **Q24/Q26:** blur and values are per image.
- **Q27-A:** one hue, the app builds the ramp.
- **D7:** Studies and Lines each have their own "apply to all"; Studies' does not copy lines (lines arrive in M3).
- **D8:** hue picker = preset swatches + a hue slider (the mockup's 8 swatches: Sepia 55°, Terracotta 35°, Ochre 85°, Sap green 135°, Teal 195°, Ultramarine 265°, Violet 305°, Neutral grey).
- **D9:** the ramp runs from near-black of the hue to its lightest tint, OKLCH lightness ≈ 0.20 → 0.95 ("tuned on real prints in M2" — the owner's print in the sign-off checklist is that tuning).
- **D1:** on phones, Lines will live inside the Studies step (M3). M2 adds the Studies step; Lines are absent until M3.
- **Spec §2.9:** default study settings are remembered in `localStorage` (what exactly counts as "default" is owner question Q5).
- **Q33:** no captions, labels or page numbers in the PDF (relevant to Q9/Q10 below).
- **Q35 / privacy:** no analytics; images and anything derived from them are never persisted or sent.

## Rulings made in this plan (technical, not product)

Each ruling is binding for the sub-plans. They are technical consequences of the spec; a reviewer who disagrees raises a contract change request.

- **M2-R1 Study settings live on the image, not in `ImageEdits`.** `ImageDescriptor` gains `study: StudySettings`. Crop/rotate/copies stay in `edits`; "apply to all" copies `study` only. Keeps `sanitizeEdits`/`editsEqual` and the edit sheet untouched.
- **M2-R2 One group per copy.** `copies = N` with `k` versions prints N groups of `k` tiles (N × k tiles). The layout key stays `${contentHash}~${occurrence}#${copy}`; only `tiles` changes. With every image at "Original only", layouts are byte-identical to M1 (golden snapshot unchanged).
- **M2-R3 Sizes are per tile.** A fixed size sets each tile's width/height (as M1 already defines `size` per tile); the 300-DPI cap and the 60 mm comfort minimum are per tile; a group too large for the page is scaled to fit as a whole and flagged `scaled-to-fit` (existing engine behaviour). See Q15; copies are Q16.
- **M2-R4 Versions follow reading order.** Versions are kept in the canonical order `original, blurred, values, blurValues` (filtered to the selected ones). `buildPageModels` sorts a placement's tile rects by `(y, x)` and assigns `versions[i]` to the *i*-th rect, so the first selected version is always top-left (left→right in a row, top→bottom in a column, including turned groups whose engine order runs right-to-left). See Q8.
- **M2-R5 Study is applied to the printed image area, before bleed.** Pipeline per tile: crop → resample → rotate/flip → **study (blur, then posterise)** on the `outW × outH` image area → bleed by edge extension of the studied pixels. Blur samples only pixels inside the tile (clamp-to-edge), never outside the crop.
- **M2-R6 Blur radius is relative to the printed tile.** Gaussian σ (px) = `blurPct / 100 × 0.05 × min(outW, outH)`, where `outW × outH` is the tile's printed pixel size at the resolution being rendered. Because σ scales with the rendered size, the low-resolution preview and the 300-DPI PDF look the same, and 40% looks alike on every photo (spec §2.6). See Q12.
- **M2-R7 Lightness = OKLab L.** Each pixel's sRGB (8-bit, gamma-encoded) is linearised (256-entry LUT) and converted to OKLab L. N equal steps over the tile's lightness range (see Q11 for which range), value *k* → ramp colour *k*.
- **M2-R8 Ramp.** `L_k = 0.20 + 0.75 · k/(N−1)`; chroma `C(t) = 0.045 + 0.05·sin(πt) − 0.02·t` (the approved mockup's curve, `t = k/(N−1)`), clamped to the largest in-gamut sRGB chroma at `(L_k, h)` minus 0.002, floored at 0; `neutral` → `C = 0`. Output colours are 8-bit sRGB. The ramp is strictly increasing in L, every colour is in gamut, and the lightest is never `#ffffff`.
- **M2-R9 Formats.** `original` and `blurred` tiles → JPEG (q 0.92, as M1). `values` and `blurValues` tiles → PNG (flat colour; spec §2.5 "flat value studies as PNG").
- **M2-R10 Memory: everything in place.** Study maths runs **in place** on the tile's `Uint8ClampedArray`; no per-pixel `Float32Array`/`Float64Array` copies. Extra memory per tile is O(max(w, h)) (one line buffer) plus a 1024-bin histogram.
- **M2-R11 Preview study tiles render in a dedicated studies worker** (`OffscreenCanvas`), using the same `renderTile` + study code as the export worker. If the worker cannot start (no `OffscreenCanvas` 2D in workers), the same function runs on the main thread with DOM canvases (no feature loss, only jank).
- **M2-R12 Preview never shows a wrong version.** While a study tile is being processed, the preview draws the last processed image for the same tile slot (same image, version and page position) if one exists, otherwise the "missing" fill; it never draws the original pixels in a study tile's place. The sheet is `aria-busy` while any of its study tiles is pending.
- **M2-R13 Warnings once per group.** Low-DPI and scaled-to-fit chips show on the first tile (reading order) of a group only; screen-reader descriptions still name every tile.
- **M2-R14 Tile names.** The accessible name of an `original` tile stays the image name (M1 E2E selectors keep working); other tiles are named "`<name>`, `<Version>`" (e.g. "pears.jpg, Blurred"). Groups of ≥ 2 tiles show a screen-only version chip on each tile and, when guides are on, a dashed group outline (design README §"Study groups get a dashed group outline on screen"). Neither is printed.
- **M2-R15 Layout memo.** The pipeline skips the layout worker when the layout items and page setup are structurally equal to the last successful run, and only rebuilds page models. A blur/values/hue change never re-runs layout; a version toggle does (the tile count changes).
- **M2-R16 Export pauses the preview studies queue.** While the export dialog is open (and so for the whole export, D-CR3), queued preview study jobs wait and retained (not currently wanted) study bitmaps are released, so the two workers never process pixels at the same time on a phone.
- **M2-R17 No new runtime dependencies.** M2 uses only what M1 installed (no image-processing or colour library). Blur, OKLCH and posterisation are written here (small, pure, tested). No `package.json` change is expected in any M2 task; if one is needed, it is a contract change request.

export const MAX_BLUR_PCT = 100

## Memory budgets (hard constraint)

A real iPhone 15 Pro Max killed the tab in M1 before #75 (22 × 24 MP HEIC). Studies multiply tiles by up to 4, so every phase has a stated budget, and the tasks that own each phase pin it with a test.

Notation: `B(w, h) = w × h × 4` bytes. `P` = one preview bitmap ≤ 2048 px long side (≤ 16.8 MB, 12.6 MB for 4:3). `F` = one full decode ≤ `MAX_CANVAS_AREA` 16.7 MP (≤ 67 MB). `T` = one 300-DPI tile canvas incl. bleed ≤ `MAX_CANVAS_AREA_PX` (≤ 67 MB; an A4 half-page tile is about 2.5 MP = 10 MB; a tile of a 3-version group on A4 about 1 MP = 4 MB).

|---|---|---|---|---|

| Preview, originals | per page: tile canvases at screen DPI for tiles on the page | nothing (original path unchanged) | 0 | — |
| Preview, study tiles | — | **wanted** study bitmaps: one per study tile on the mounted pages, at screen DPI. Their total area ≤ the sheet canvases' area (tiles never overlap), so ≤ pages × `B(deviceW, deviceH)`; each sheet ≤ 16.7 MP | ≤ the sheet canvases (already bounded in M1) | C1 unit: total wanted bytes ≤ sum of sheet areas for random page models |

## Testing strategy (spec §7, M2 additions)

- **Pure maths (A2–A5, node, Vitest + fast-check):**
  - OKLCH: round trips sRGB → OKLab → sRGB within 1/255 on all 8-bit greys and 10 000 random colours; reference values from Ottosson's published table (white L = 1, black 0, sRGB red L ≈ 0.6279); `maxChroma` is in gamut and `+1e-3` is not; `lightness8` equals `linearRgbToOklab(...).L`.
  - Blur: radius scaling (`blurSigmaPx(100, 400, 300) = 15`, `(40, 300, 400) = 6`, linear in pct, uses the short side); a constant image stays constant; **average brightness is kept** (spec §7) within 0.5 levels on images whose border ring of width ≥ 3σ is constant, plus a proven edge bound for any image (A-CR2); blur never increases the range (min/max); alpha untouched; σ < 0.25 is a no-op; one-pixel-wide and one-pixel-tall images; the 3 box radii approximate σ (variance of the composed kernel within 5% of σ²).
  - Ramp: length N for N = 2..20; **monotonic: strictly increasing OKLab L** (re-measured from the 8-bit output); first L ≈ 0.20, last ≈ 0.95 (±0.01); every colour in gamut; the lightest is never `#ffffff` (R7) for every hue 0..359 and neutral; non-neutral ramps keep their hue (±3° where C > 0.02); neutral ramps are greys (r = g = b).
  - Posterise: **exactly N distinct colours** for a full-range gradient (N = 2..20), all of them ramp colours; **N equal steps** (bin edges at `lo + k(hi − lo)/N`, pinned with hand-built pixels just below/above each edge); **2-value notan** gives only `ramp[0]` and `ramp[1]` split at the midpoint of the range; a flat image maps to one middle value; percentile clipping pinned with 2% outliers; output alpha 255.
  - `applyStudy`: blur-then-posterise order pinned (a fixture where posterise-then-blur would give more than N colours); `blurValues` output has ≤ N colours; `values` ignores blur; golden images: 4 synthetic 96 × 64 images × 4 versions hashed (FNV-1a over the bytes) into a snapshot, regenerated only for an intended change.
- **Model / store / settings (A1, B1, B2):** `sanitizeStudy` idempotent and total (property); `withVersion` never empties; canonical order; `studyKey` injective over sanitized studies (property: different `TileStudy` ⇒ different key); store `updateStudy` no-op identity, `applyStudyToAll` copies versions too, counts, keeps edits; new imports take the default study; settings v1 → v2 migration and partial-corruption cases.
- **Layout (B3):** `tiles = versions.length`; golden snapshot unchanged (all "Original only"); group invariants from M1's `expectLayoutInvariants` (groups on one page, gutter between tiles, inside the safe area) on items with 1–4 tiles; fixed size with versions; copies × versions; perf case.
- **Render (B4, B5):** page-model snapshot with a 3-version group (reading order for row, column, turned row, turned column — four hand-built placements, mutation-checked: reversing the sort must fail); `groups`; `tileRenderKey` differs per version/study and is equal for identical copies; `renderTile` applies the study before bleed (fake canvas records the call order); worker API encodes PNG for value versions and JPEG otherwise; `composePdf` round trip: a page with original + blurred + values tiles parses back with 2 `DCTDecode` and 1 `FlateDecode` image, the PNG has exactly 5 colours.
- **Preview (C1–C3):** provider queue order, cancellation of unwanted queued keys, concurrency 1, stale-slot display, LRU retention bound, closing on eviction/removal/pause, failure isolation (fake renderer); worker API with a fake `OffscreenCanvas` factory; PagePreview draws study tiles from the provider, never the original pixels in their place, sets `aria-busy`, names tiles, chips once per group, outlines with guides on.
- **UI (D1, D2):** Testing Library behaviour tests for every control (keyboard: arrows on sliders, Space/Enter on chips and swatches; the last-chip rule; apply-to-all announcement); tabs; Studies step order; defaults effect.
- **E2E (D3, D4), every spec with the strict network guard:**
  - **D3 X-S1 (exit criterion, chromium + firefox + webkit):** upload the new `value-ramp.png` fixture (a 900 × 600 smooth two-axis gradient covering the full lightness range, committed by D3 with its generator in `__fixtures__/generate.mjs`), select Original + Blurred + Values with N = 5 and Sepia, export A4. Parse the PDF: 1 page, 3 image draws of equal size, side by side in reading order (same y, x increasing, gap = gutter 6 mm ± 0.1 mm) or stacked (same x, y increasing) per the group arrangement; draw 1 and 2 are `DCTDecode`, draw 3 is `FlateDecode` with exactly 5 colours; the three images differ (distinct XObjects); preview tile boxes equal the PDF boxes within 0.5% (M1's preview-equals-PDF check, extended to groups).
  - D3: blur + values (PNG, ≤ N colours), notan (N = 2 → 2 colours), neutral grey (r = g = b), apply to all (every image gets the same versions; page count grows), versions with copies and a fixed size, axe on the Studies tab (light/dark, a group selected), keyboard-only study editing, privacy P1/P2 extended (storage holds `studyDefaults` and nothing image-derived; no request during study preview and export).

### New questions raised by M2

Q1. **Versions for newly added photos.** Which versions does a photo get when it is added?
   _Recommendation:_ Original only. Adding photos then never multiplies pages by surprise; you turn studies on per photo or with "Apply to all". (The mockup shows three versions ticked for one selected photo, as an example.)
   **A:**

Q2. **Default blur amount.**
   _Recommendation:_ 40% (as in the mockup): σ = 2% of the tile's short side, a clear squint.
   **A:**

Q3. **Default number of values.**
   _Recommendation:_ 5 (as in the mockup and the exit criterion).
   **A:**

Q4. **Default hue.**
   _Recommendation:_ Sepia (55°), the first swatch, as in the mockup.
   **A:**

Q5. **Which study settings are remembered between visits?** The spec (§2.9) says "default study settings" are saved. What counts as the default?
   _Recommendation:_ the **last used** blur %, number of values and hue (including Neutral grey) are remembered and given to newly added photos; the **versions are not remembered** (new photos start as Original only, Q1). Nothing about the photos themselves is saved.
   **A:**

Q6. **Does "Apply to all images" also copy the version selection?**
   _Recommendation:_ yes. It copies everything on the Studies tab: versions, blur, values and hue (the mockup's hint says "Copies these study settings"). It never copies crop, rotation, copies or size.
   **A:**

Q7. **Confirm before "Apply to all images"?** It overwrites every other photo's study settings and there is no undo.
   _Recommendation:_ no confirmation, but announce the result ("Study settings copied to 6 images") and keep it reversible by hand. (M1 asks before "Remove all" because photos are lost; here nothing is lost.)
   **A:**

Q8. **Order of the versions within a group.**
   _Recommendation:_ always Original, Blurred, Values, Blur + Values (skipping unticked ones), in reading order: left to right in a row, top to bottom in a column, also when the engine turns the group to pack it.
   **A:**

Q9. **Labels on the printed sheet.** Should printed tiles carry a small "Blurred" / "Values" label?
   _Recommendation:_ no. The spec's Q33 rules out captions in the PDF. Labels appear only on screen (version chips in the preview).
   **A:**

Q10. **A value legend (swatch strip) for value studies.** Should the PDF print the N ramp colours next to a value study, so you can mix paint to match?
   _Recommendation:_ not in M2 (Q33: no extra marks in the PDF). The Studies tab shows the ramp on screen. Could be revisited in M5 as an option.
   **A:**

Q11. **What range of lightness is split into N steps?** The spec says the image's lightness is "split into N equal steps".
   _Recommendation:_ the photo's **own** range: its darkest dark becomes value 1 and its lightest light value N (ignoring the extreme 1% at each end, so a few specks don't decide the scale). This is how a painter maps a scene onto a value scale, and every study uses all N values. The alternative is a fixed scale from black to white, where a dark photo would use only the lower values.
   **A:**

Q12. **"Image size" for the blur amount.** The spec scales blur with the image's short side (100% ≈ 5%). For a cropped photo, which short side?
   _Recommendation:_ the short side of the **printed tile** (after crop), so the same % looks alike on every printed tile, whatever its crop or print size.
   **A:**

Q13. **Unticking the last version.** What happens if you untick every version?
   _Recommendation:_ the last ticked version can't be unticked (its chip is disabled, with the hint "At least one version prints"). To leave a photo out, remove it.
   **A:**

Q14. **Blur and values controls when their version is off.** Should the blur slider be disabled while neither Blurred nor Blur + Values is ticked (and the values controls while neither Values nor Blur + Values is)?
   _Recommendation:_ keep them enabled, so you can set them up before ticking the version; the hint under each section says which versions use it.
   **A:**

Q15. **Fixed size with several versions.** A photo with a fixed width of 100 mm and three versions: what prints?
   _Recommendation:_ three tiles, each 100 mm wide (the size applies to each tile). If the group does not fit the page, the whole group is scaled down together and marked "Scaled to fit", as today.
   **A:**

Q16. **Copies with several versions.** A photo with 2 copies and three versions: what prints?
   _Recommendation:_ two complete groups (six tiles), each group kept together on one page.
   **A:**

Q-budget. **Memory budget for the phone test.** The CI memory test (22 × 24 MP photos, now with 3 versions each) keeps M1's budgets: under 1500 MB after import and under 1700 MB during export.
   _Recommendation:_ keep the M1 budgets. If studies push past them, treat it as a bug to fix rather than raising the budget, and come back to you only if a fix is impossible.
