# M4 — AI-assisted lines: Overview & Shared Contracts

> **Status:** draft for owner review. Nothing in M4 starts until the owner approves this plan and answers (or accepts the defaults of) the **Questions for the owner** at the end. **Q1 (the MediaPipe version and Google's usage metrics) blocks task C2 and everything after it.**

> **For agentic workers:** this is the umbrella document for M4. It is **not** executed on its own. M4 is split into five sub-plans (A–E below), each executed with superpowers:subagent-driven-development, exactly like M1–M3. Every sub-plan treats the **Shared contracts** section of this file as binding. A sub-plan that needs a contract change lists it under "Contract change requests" instead of silently diverging.

**Goal:** Ship `v0.4.0`. Each image can carry three **guides from the photo**, each off by default, per image, with the image's line style and "Apply lines to all":

- an **edge outline** found by our own integer Canny edge detector in a worker, with an adjustable detail level;
- **face construction lines** (Loomis/Asaro: centre line, brow line, eye line, nose line, chin line, cranium circle) built from MediaPipe Face Landmarker landmarks;
- **body pose lines** (a gesture stick figure) built from MediaPipe Pose Landmarker landmarks.

The MediaPipe runtime and models are served from our own site, downloaded only when the user first asks for a guide that needs them (with progress), and kept in the browser's Cache Storage. A service worker keeps the app itself available offline. Guides are vector paths in the same page model as the M3 lines, so the preview equals the PDF. Nothing derived from a photo is ever sent or persisted. When nothing is found, the panel says so ("No face found in this image.").

**Spec:** `docs/spec.md` §2.8 (AI-assisted lines), §2.7 (lines are per image, on every printed version, vectors), §2.9 (defaults remembered; nothing derived from images is saved), §2.12 (phone flow), §3 (privacy: "The only network requests are the app's own files, AI models, and URL images the user asks for"; bundle: "AI models … load only when needed"), §4 (`lines/` "AI lines (M4)"; `public/models/` "self-hosted MediaPipe models (M4)"), §5 (`@mediapipe/tasks-vision`), §7, §8 "M4", §9 ("MediaPipe model size / browser differences: loaded only when needed, cached, falls back to the CPU; the feature is optional"), Q29 (edge, face and pose lines are optional, switched on by the user), Q30 (a one-time 5–30 MB download, cached, everything on the device), Q35 (no analytics), R8, review round 1 "No decision needed" note (the mockups' 4 MB / 9 MB are placeholders; real sizes measured in M4). **Design:** `design/lines.html` (the "Guides from the photo" section: Edge outline + Detail slider, Face construction with the one-time download box, Body pose with a download hint; the `edge`, `face` and `pose` overlays), `design/errors.html` (E3 "No face detected", E6 "Model download failed"), `design/mobile-flow.html` (Face construction inside the phone Lines section), `design/mockup.css` (`.tile__lines .joint` filled dots, `.ai-box`), `design/mockup.js` (fake download progress: "1.2 of 4 MB"), `design/README.md` (open question 6: model sizes). **Conventions:** `CLAUDE.md`. **Constraints carried over:** the M1–M3 overviews' contracts and rulings, the ledgers (`docs/superpowers/ledgers/m1-*.md`, `m2.md`, `m3.md`) and `HANDOVER.md`.

**M4 exit criteria (spec §8):**

- **It works offline once the models are cached.** Proven by E2E G-X1 (E3): with the face and pose models downloaded once, the browser goes offline, the app is reloaded (served by the service worker), a photo is added, and face, pose and edge guides appear in the preview and the PDF. It runs on chromium (required) and firefox; Playwright's WebKit can't reload offline through a service worker (`C1-R1`), so WebKit offline is checked by the owner on the iPhone in airplane mode (sign-off checklist).
- **Nothing is uploaded.** Proven by E2E G-X2 (E3): the strict network guard sees, for a session that downloads both models, detects faces, poses and edges, and exports, only same-origin GETs with no body; the only new requests are the runtime and model files under `/artistica/`; none carries a photo (no body, no query). Backed by a build-time audit (C2) that fails if a shipped chunk names a remote host, and by a fetch guard inside the AI worker (M4-R4).
- All tests green, on all required checks.
- Unit coverage ≥ 80% on the M3 list plus, new, **`src/features/lines/guides/**`**, **`src/features/lines/edges/**`** and **`src/features/lines/detect/`** pure files (workers, components and test-support excluded as today).
- The memory test M3 (`e2e/mobile-flow.spec.ts`, 22 × 24 MP photos × 3 versions, every line on) passes with **edge, face and pose guides on for every photo**, within the budgets (1500 / 1500 / 1700 MB, plus the new guides phase under 1500 MB), and the owner's real-iPhone run with guides does not crash.

## Rulings made in this plan (technical, not product)

Each ruling is binding for the sub-plans. Rulings marked "(owner Qn, default)" implement a recommended default and change only if the owner answers otherwise.

- **M4-R1 MediaPipe version: `@mediapipe/tasks-vision@0.10.35`, pinned exactly (owner Q1, default).** It is the newest release that sends nothing to Google: 1.0.0 and later POST usage metrics to `odml.pa.googleapis.com` with no opt-out, which breaks "no analytics, ever" and the spec's list of allowed requests. Upgrades are allowed only to a version whose shipped files pass the C2 host audit; bumps of this package are never auto-merged.
- **M4-R2 Assets are self-hosted and versioned.** The runtime comes from the npm package: the `virtual:ai-assets` plugin emits `wasm/vision_wasm_module_internal.js` and `.wasm` as `dist/assets/vision_wasm_module_internal-<first 8 hex of the pinned SHA-256>.{js,wasm}` (`emitFile`, whether or not anything imports the module), and the dev server serves the same files at the same URLs, so dev and build use identical URLs and a new version is a new URL (ruled in C2). The models are committed under `public/models/` with their version in the name (`face_landmarker-float16-1.task`, `pose_landmarker_full-float16-1.task`), beside `public/models/NOTICE.md` (source URL, SHA-256, licence, model-card links). A build-time module `virtual:ai-assets` exports each asset's URL, size and SHA-256; a unit test recomputes the committed models' SHA-256.
- **M4-R3 One download path: the AI asset loader.** Every runtime and model byte is fetched by `loadAiAsset` (C3): Cache Storage first (cache `artistica-ai-v1`, keyed by the asset's versioned same-origin URL), else a streamed `fetch` with progress, SHA-256 checked against the manifest, then stored; a cache read is checked the same way (ruled in C3). The worker gets the runtime as `blob:` URLs and the model as `modelAssetBuffer`; MediaPipe itself never fetches. Entries not in the current manifest are deleted on first use. Nothing is fetched until the user asks for a guide (Q30).
- **M4-R4 The AI worker cannot reach other origins.** Before MediaPipe is imported, the worker replaces `fetch`, `XMLHttpRequest.prototype.open`, `importScripts`, `self.import` (MediaPipe calls it before `import()`, `C1-R1`), `WebSocket` and `navigator.sendBeacon` (where present) with guards that throw for any URL that is not `blob:`, `data:` or same-origin under the app's base. A refused request is reported to the main thread as an error (it fails tests), never swallowed.
  - **Extended by the C4 review (binding):** the guard also covers `EventSource`, `WebTransport`, `WebSocketStream`, `Cache.add`/`addAll` and `FontFace` with a CSS source, and refuses every `Worker`, `SharedWorker` and `BroadcastChannel` whatever the URL (a nested worker runs unguarded). It converts each URL to a string once and hands the native API that string (a native `Request` is read through `Request.prototype`'s own `url` getter), calls the natives through `Reflect.apply`, and keeps `URL`, its getters, `String` and `startsWith` from install time, so a later change to them cannot open it. The prototype `constructor` of each guarded class is the guarded one. Native `import()` syntax cannot be intercepted from script: MediaPipe uses `self.import` (guarded) whenever it exists, and the build-time host audit (C2) is the backstop for the shipped code.
- **M4-R5 Landmarks run in a module worker on the CPU delegate.** `FaceLandmarker` and `PoseLandmarker` are created in `src/features/lines/detect/landmark.worker.ts` with `delegate: 'CPU'`, `runningMode: 'IMAGE'`. A main-thread engine with the same API is the fallback when the worker can't start (as M2-R11). Spike C1 checks both in chromium, firefox and webkit (the iPhone is checked at M4 sign-off instead: owner, 2026-10-08); if the worker fails on WebKit, C1 records it and C4 makes the main-thread engine WebKit's default (contract unchanged).
  - **Adjusted by C1 (`C1-R1`), binding for C4:** the worker stays the default on every engine, WebKit included: it works wherever the worker has WebGL. The CPU delegate still uploads every input image through WebGL (`_addBoundTextureAsImageToStream`; there is no CPU image path in 0.10.35), so **the engine chooses by WebGL capability, never by user agent**: the worker when `new OffscreenCanvas(1, 1).getContext('webgl2')` (or `'webgl'`, MediaPipe's own fallback) succeeds inside it; else the main-thread engine when a page canvas has WebGL (CI's Linux WebKit); else the detection fails with `reason: 'unsupported'` (CI's Linux Firefox, a browser with WebGL off; what the panel says then is owner Q15). The main-thread engine imports the module loader itself and sets `globalThis.ModuleFactory` before each `createFromOptions` with an empty `wasmLoaderPath` (MediaPipe's own main-thread path injects a classic `<script>`, and the module loader has an `export default`, so it can't load that way).
  - **Runtime loading (C1, binding for C4):** the wasm `Blob` is typed `application/wasm` (MediaPipe uses `instantiateStreaming`). MediaPipe clears `self.ModuleFactory` after each `createFromOptions`, and a second `import()` of the same URL doesn't re-run the module, so every landmarker creation gets either a fresh `blob:` URL of the loader or `globalThis.ModuleFactory` set again from a loader imported once (the main-thread engine's way). Creating a second landmarker from the same loader URL fails with `ModuleFactory not set.`
- **M4-R5a One landmarker loaded at a time (owner, 2026-10-08; binding for C4, D2, E4).** Face and pose are never loaded together. The engine holds at most one landmarker instance; switching from face to pose (or back) calls `close()` on the loaded one and drops every reference to it before creating the other; the FIFO (M4-R6) serialises the jobs, so a switch happens only between jobs. A switch costs one landmarker creation (53–210 ms in C1). Reason: with both loaded, the browser grows +368–387 MB and the guides phase reaches 1526–1545 MB, over the 1500 MB budget; one at a time grows +279–303 MB, 1437–1461 MB (`C1-R1`). The 1500 MB budget is unchanged.
- **M4-R6 One detection at a time; the AI worker is released when idle.** Landmark detections run one at a time in a FIFO (edges have their own worker and queue), with one landmarker loaded at a time (M4-R5a). The landmark worker is terminated as soon as the scheduler's landmark queue drains, which frees its WebAssembly memory; the next detection starts it again from Cache Storage, with no network. The engine's own 30 s idle release (`LANDMARK_IDLE_MS`) stays as a backstop (ruled in "Guides memory", 2026-10-10; the plan said 30 s).
- **M4-R7 What is analysed.** Face and pose: the image's preview bitmap (≤ 2048 px) **rotated by the user's rotation** (not cropped, not flipped), so a photo the user turned upright is analysed upright. Edges: the **cropped** picture from the preview bitmap, scaled so its long side is at most `EDGE_ANALYSIS_LONG_SIDE = 1024` px (unrotated, unflipped), so the detail follows what prints. Results are converted back to **source coordinates** (normalised to `pxW × pxH`) before they are stored (A2 helpers), so flips and the engine's turn never re-run a detection (owner Q9, default).
- **M4-R8 Detections are cached per content and parameters, in memory only.** Keys carry the kind, so face and pose of one image never share an entry: face `face|${contentHash}|r${rotation}`, pose `pose|${contentHash}|r${rotation}`, edges `edges|${contentHash}|${cropKey}|d${detailPct}` (`cropKey` = the crop rounded to whole source px, or `full`). Twins share results. A result stays while its photo (content hash) is present, so a guide switched off and on again, or a rotation turned back, reuses it; at most 4 edge entries per content hash (least recently used dropped, never one an image prints). Removing the last image with a content hash drops its entries; "Remove all" drops everything. Never persisted (§2.9).
- **M4-R9 Settings never change because of a result.** A guide switch stays on when nothing is found; the panel says so and nothing prints (owner Q7, default). So `linesKey`, duplicate ranking (M3-R17) and the layout never depend on asynchronous results.
- **M4-R10 Guides are geometry in source pixels, mapped by one affine.** A2's `sourceToFrame(img, frame)` is the exact affine from source px to the picture frame (crop, then the user's rotation, then flips, then scale), composed with `frameToPage`. Circles are built in source px, where pixels are square, and stay circles on paper because the layout never changes a picture's aspect.
- **M4-R11 Guides join the solid batch.** Per tile, the solid stroke holds the composition paths (M3 order), then edges, then face guides, then pose guides (`LINE_TYPES` order); the dashed batch still holds only the centre lines. One stroke means overlapping guides never darken each other below 100% opacity (M3-R7). The PDF and preview code are unchanged; their operator and call tests gain guide cases (D3).
- **M4-R12 Pose joints are dots made from strokes.** A joint is a circle of radius `widthMm / 2` stroked at `widthMm`, which paints a solid disc of radius `widthMm`: no fill operator, no `/ca`, no new renderer code. Built at the page-model stage because the radius depends on the style.
- **M4-R13 Face construction (owner Q3, default).** From one face's landmarks, in source px:
  - head axis: `u` = unit vector from the right eye's outer corner (33) to the left eye's outer corner (263); `n` = `u` turned 90° towards the chin (sign chosen so `(p152 − p10)·n > 0`);
  - **centre line** (the midline): the polyline through the 28 midline landmarks from 10 to 152 (`MIDLINE` in `guides/face.ts`, verified in A3 Step 1), preceded by a straight segment from the top of the cranium circle (`centre − r·n`) to 10;
  - **eye line** through the iris centres' midpoint (468, 473); **brow line** through the midpoint of the brow arcs' high points (105, 334); **nose line** through the base of the nose (2); **chin line** through 152; each along `u`, from `lo − 0.1·(hi − lo)` to `hi + 0.1·(hi − lo)`, where `lo` and `hi` are the least and greatest `p·u` over all 478 landmarks, so each overhangs the face by a tenth of its width on both sides, in a ¾ view too (A3 ruling);
  - **cranium circle** (Loomis ball): centre where the brow line meets the centre line, that is where the line along `u` through the brow midpoint crosses the midline polyline; when the brow level is beyond the polyline's ends, the point at the brow level on the line along `n` through the nearest end vertex. Radius = the brow-to-nose distance along `n`, so the circle reaches down to the nose line. The mockup (`design/lines.html`) draws its circle above its brow line; Q3, which this rule follows, puts the centre on it;
  - **jaw line** (as mocked): the face-oval ring from 234 through 152 to 454 (`JAW`, 21 points);
  - command order: circle, centre line, brow, eye, nose, chin, jaw (63 commands, `MAX_CMDS_PER_FACE` = 160);
  - a face is dropped (no commands) when its landmark box doesn't meet the crop, a landmark is not finite, it has fewer than 478 points, or the nose base is not below the brow crossing along `n` (this includes coinciding eye corners).
- **M4-R14 Pose figure (owner Q4, default, as mocked).** From one pose, in source px: a head circle centred between the ears (7, 8), radius 0.75 × the ear distance (when an ear is hidden: radius 0.25 × the shoulder width, and the centre on the segment from the visible ear to the nose (0), at the fraction `EAR_HALF_PER_EYE_SPREAD = 7.25 / 6.3` × the eye distance (2–5) ÷ the ear–nose distance, 0 when an eye is hidden, clamped to [1 − r/d, 1] (*d* the ear–nose distance), with the radius raised to at least the distance from the centre to the ear, so the circle contains both the ear and the nose: on the nose facing the camera, on the cranium in 3/4 and profile (A4 Ruled item 3)); a head whose radius would be 0 is not drawn; the radius is never less than 0.85 × the distance from the nose to the farther visible ear, so a head turned to profile, whose ears overlap, keeps its size (A4 review); with an ear hidden, the head needs both shoulders or the other ear, else it is not drawn; neck from where the line from the head centre to mid-shoulders leaves the head circle (the lowest point for an upright figure) to mid-shoulders; spine mid-shoulders → mid-hips; shoulder line 11–12; hip line 23–24; arms 11–13–15, 12–14–16; legs 23–25–27, 24–26–28; joint dots at both shoulders, elbows, wrists, hips, knees, ankles, mid-shoulders and mid-hips. A segment is drawn only when both ends have `visibility ≥ 0.5` and lie inside the image; a dot only at a drawn segment's end. Hands, feet and face points are not drawn.
- **M4-R15 Edge core is integer arithmetic.** Grey = `(77R + 150G + 29B) >> 8`; binomial 1-4-6-4-1 blur passes; integer Sobel; squared magnitude; direction sector by integer comparison (`|gy| · 99 ≤ |gx| · 41` for "horizontal", the mirror for "vertical", else diagonal: tan 22.5° ≈ 41/99); thresholds from the sorted survivor magnitudes (B1-R5); hysteresis with an explicit stack; 8-connected tracing in a fixed scan order. No `atan2`, `Math.hypot` or `exp`, so the same pixels give the same outline bit for bit in every engine. Engines differ only through the browser's own decode and scaling.
- **M4-R16 Detail mapping and the path budget.** `detailPct` 1–100 (default 50, as mocked) maps, through a pure table pinned by tests, to the share of strongest gradient pixels kept (3% → 20%) and the shortest chain kept (48 px → 6 px); the blur is the same 2 binomial passes at every detail, so a higher detail keeps every edge pixel a lower one has (B1-R1). Chains are simplified with Ramer–Douglas–Peucker (ε = 1 analysis px, distance to the segment, B2-R1), then kept longest first up to **`MAX_EDGE_VERTICES = 4000`** per image: longest is the chain's pixel count before simplification (a closed chain counts each pixel once), ties by its first point's scan index; a chain that would overflow the budget is skipped and shorter ones are still tried (B2-R2). The PDF cost is pinned at ≤ 120 KB of compressed content per tile at the budget (measured in D3).
- **M4-R17 Per-tile bound.** `MAX_GUIDE_CMDS_PER_TILE = 6000`: edges 4000 + up to four faces × 160 + up to four poses × 160 (A3 and A4 pin the per-face and per-pose bounds). The M3 bound (200) still holds for composition paths alone.
- **M4-R18 Export waits for running guides.** While a detection or download that a printed image needs is in progress, Export is disabled with the reason "Finding guides in your photos…" (a new `exportBlock` reason, `guides`), so the PDF always equals the preview. A failed or empty result does not block. **Rule (E2 review):** a switched-on guide of a printed image blocks until its status is settled: `done`, `failed` or `needs-download`. No status yet (the moment after the switch, a rotation or a crop, before the scheduler has seen it, or while it checks whether the model is cached), `running` and `downloading` all block, and so does a Detail value still inside its 80 ms settle (`useDetailDraft`, read by `useExportGate`; E3 review); `needs-download` does not, because nothing happens until the user taps "Download & turn on", and the box is on screen. A detection result marks the pages as updating in the same store update (`PipelineEffect` subscribes to the detections store), so Export never sees a result before the page model carries it. **`DOWNLOAD_STALL_MS` = 30 s:** a download that receives no new bytes for 30 s (from the click, or since its last bytes) is aborted and fails as `failed: download`, the same "Couldn't download…" alert with "Try again", so a stalled connection cannot hold the gate.
- **M4-R19 Downloads need a click (owner Q10, default).** Switching a guide on for a model that isn't cached shows the mocked box "One-time download: N MB … Download & turn on"; nothing is fetched until that button is pressed. N comes from `virtual:ai-assets` (the model, plus the shared runtime if it isn't cached yet), in MB to one decimal.
- **M4-R20 Offline app shell (owner Q11, default).** A hand-written service worker (`src/sw/sw.ts`, built to `dist/sw.js`, scope `/artistica/`) precaches every built file except the AI runtime, the models, `og-image.png` and source maps; navigations are network-first with the cached page as the fallback (after a network error, or after 5 s without an answer: C5-R1); hashed assets are cache-first; non-GET requests, other origins (link imports), `blob:` and the AI assets are never touched. No `skipWaiting`: a new version takes over once every tab of the old one has closed, so a running tab never loses its lazy chunks. Registered only in production builds, from the app page. Playwright blocks service workers (`serviceWorkers: 'block'`) except in the offline spec. A kill-switch build replaces a broken worker (C5-R2).
- **M4-R21 One new dependency.** `@mediapipe/tasks-vision@0.10.35` (a runtime dependency) is the only `package.json` change in M4 (C2). The service worker, edge detector, loader and hashing (`crypto.subtle.digest`) need no new packages.
- **M4-R22 The page description names the guides** like other lines ("portrait.jpg, 120 × 160 mm, lines: Rule of thirds, Face construction"). It lists the switched-on types, whether or not anything was found; the panel reports the result.

## Determinism

- **Layout:** guides never change layout items; `linesKey` includes only switches and the detail (M4-R9), so duplicate ranking and the golden snapshot are unchanged for M3 settings and deterministic with guides.
- **Edges:** integer core (M4-R15) gives the same outline for the same pixels in any engine; a golden test pins the polylines of a synthetic image (B2). The pixels themselves come from the browser's decode and scaling, so outlines can differ *between* engines but never between runs.
- **Landmarks:** MediaPipe on the CPU delegate is expected to repeat run to run on one device; C1 measures it (detect the fixture 10× in each engine: maximum coordinate difference). Whatever C1 finds, a detection runs **once per key** per session (M4-R8), and the preview and the PDF read the same stored result, so preview = PDF always holds. If C1 finds run-to-run differences, landmarks are rounded to 1/4096 of the bitmap side before storing (C4), and E3's determinism test compares with a 0.5 mm tolerance instead of equality.
  - **Ruled by C1 (`C1-R1`): bit-identical, no rounding, no tolerance.** On the CPU delegate, 10 detections on one landmarker, a detection in a fresh worker, and a detection on the main thread gave the same landmarks bit for bit (max |Δ| = 0 over x, y, z) for face and pose, in every engine that could run them (chromium, mobile-chromium, firefox, webkit, mobile-webkit locally; chromium and mobile-chromium on CI). C4 does **not** round, and E3's determinism test compares with equality within one engine. Engines differ from each other (WebKit vs Chromium/Firefox on the same 2048 px JPEG: up to 4.7·10⁻⁴ of the image for face, 7.9·10⁻³ for pose; Chromium and Firefox agree exactly), so no test compares landmarks across engines. The GPU delegate differs from the CPU by up to 1.2·10⁻², which is why CPU stays the only delegate.
- **`tileRenderKey`** is unchanged: guides, like lines, never touch tile pixels (M3-R5), so a detection result never re-renders, re-encodes or re-embeds a tile, and never re-runs a study job.

## Testing strategy (spec §7, M4 additions)

- **Model (A1):** `sanitizeLines` property extended to the guide fields (garbage, NaN, out-of-range detail); `linesKey` identical to M3 for every setting with guides off (property against a frozen copy of the M3 function) and injective with guides; `activeLineTypes` order; `withoutLineTypes` turns guides off and keeps the detail.

- **Face and pose (A3, A4):** built from a **recorded landmark fixture** (the real detector's output on the face and body fixtures, captured once by C1 and committed as JSON): the eye line through both irises, the brow line above it, the nose and chin lines below it, all parallel to the eye axis; the circle's centre on the brow line and its radius = brow–nose distance; the centre line passes through 10 and 152; a tilted face (fixture rotated by 20°) gives lines rotated by 20°; mirror symmetry of a mirrored face; bounds `MAX_CMDS_PER_FACE`/`POSE`; hidden landmarks drop exactly their segments.

- **B1-R1 (controller, 2026-10-08), M4-R16 blur.** The table's blur passes (3 → 0) made edge pixels drop where a pass is removed (detail 33 → 34, 66 → 67, 99 → 100; 28 of 120 such steps on noise went down), which breaks the owner's sign-off line "the outline gets denser as Detail goes up". `blurPasses` is now `EDGE_BLUR_PASSES = 2` at every detail; `EdgeParams` keeps the field. Two passes chosen on real photos (B1 review, edge maps at blur 0–3 × detail 1, 25, 50, 75, 100): 0 and 1 draw feather and fur texture as hatching from mid detail up; 3 is the cleanest but loses inner shapes at low detail; 2 gives the main shapes at 50 and still gets denser up to 100. - **B2-R1 (reviewer, 2026-10-08), RDP distance.** RDP measures each point's distance to the segment AB, not to its infinite line: `cross²` when the point projects inside AB, `|AP|² · |AB|²` before A and `|BP|² · |AB|²` past B, compared with `ε² · |AB|²` (all integers; when A = B, the distance to A). The line distance breaks "every dropped point is within ε of the kept polyline": a hairpin's tip lies on the line but far from the segment. A point exactly ε away is dropped; of equally far points the first is kept.
- **B2-R2 (reviewer, 2026-10-08), budget fill.** Chains are visited longest first (pixel count before simplification; ties by the first point's scan index) and each is kept if its simplified vertices still fit in `MAX_EDGE_VERTICES`; one that does not fit is skipped and shorter ones are still tried. A strict prefix would stop at the first chain that overflows and could leave most of the budget unused, which is not the dense outline M4-R16 asks for; the greedy fill is just as deterministic.
- **B2-R3 (reviewer, 2026-10-08), transpose.** The outline is not pinned under a transpose: tracing follows the scan order, so a transposed edge map splits into different chains in a different order. The property that does commute, which pixels the outline traces, follows from B2's exact-cover property with B1's transpose test.

- **C3 (reviewer, 2026-10-08), the AI asset loader.** Contract changes, all reflected in the contract above:
  1. **Cache reads are verified.** A cache hit is checked against the manifest size and SHA-256; an entry that does not match, or that cannot be read, is deleted and downloaded again, so a corrupt entry never reaches MediaPipe. Cost, measured on 20.9 MB (runtime wasm 11.2 MB + loader 0.3 MB + pose 9.4 MB, the largest model): SHA-256 median 9 ms in Chromium, 11 ms in Firefox and 8 ms in WebKit (macOS arm64); 36 ms and 62 ms in Chromium at a 4× and 6× CPU throttle; a whole verified cache hit of the three files 16 ms, 63 ms at 4×, 105 ms at 6×. Well under the 300 ms bound on a phone-class throttle. It runs once per engine load: the scheduler keeps the bytes while the engine lives (D2).
  2. **Abort is per caller.** Calls for one asset share one download; each has its own progress callback and abort. An abort rejects only its own caller (with the signal's reason); the fetch is aborted only when every caller has aborted, and an aborted or failed download is forgotten, so the next call starts again. An abort that lands while the bytes are hashed still stores nothing. Without this, D2's no-signal landmark load and the user's abortable download would cancel each other.
  3. **Callers sharing a download get the same `ArrayBuffer`.** Binding for C4 (repeats the D2 note): `prepare` never transfers or detaches the buffers it is given; to send bytes to the worker by transfer, it copies first.   4. **`createLandmarkEngine(overrides?)`** takes optional `{ pageHasWebGL, main }` test seams; `createLandmarkEngine()` is the contract call. `createLandmarkEngineWith` and `createMainThreadBackend` are exported for tests.
  5. **The bytes reach the worker by structured clone, not transfer**, following the C3 and D2 rulings (`prepare` never detaches its buffers; a clone costs the one copy a transfer of a copy would). They are sent only when the worker (re)starts or the model changes. C4 Step 2's wording is corrected.
  6. **The 30 s `LandmarkTimeout` covers each queued call, `prepare` included** (worker start and landmarker creation), so a stalled start cannot hold the export gate (M4-R18). A timeout terminates the worker; the next call starts one and prepares it again from the bytes it was given.
  7. **The main-thread fallback loads `landmark-api.ts` and its own copy of `vision_bundle` lazily**, never in an initial chunk; the perf-budget line above is corrected. `scripts/check-bundle-budget.ts` fails the CI `build` job (required, no `if:` or `continue-on-error`) when an initial chunk contains `FaceLandmarker` or `PoseLandmarker`; the minified `vision_bundle` keeps the name, so the check sees it.
  8. **Main-thread creations are serialised.** On the main thread a timed-out or disposed backend cannot stop a creation already under way, so every main-thread backend's `prepare` waits for the previous one to finish (and be closed). Without this a timeout, or D2's dispose-then-create, held two landmarkers at once (M4-R5a).
  9. **The landmark worker and its `vision_bundle` chunk are emitted into `dist` and precached by C5's shell** as app assets (checked in the built `sw.js`), which offline face and pose need (G-X1); once E2 wires the engine, the main-thread fallback's lazy chunks are precached the same way. Only the runtime and the models stay out of the shell (C3's cache holds them).

- **A4 (reviewer, 2026-10-09), pose figure.** M4-R14's text is corrected:
  1. **Neck start.** The neck starts where the line from the head centre to mid-shoulders leaves the head circle, not at the circle's lowest point in source px. The two are the same for an upright figure; for a reclining figure, or a photo the user turned (detections are in source px, M4-R7), the lowest point is beside the head and the neck would leave the circle away from the shoulders. When the head centre is on mid-shoulders, the neck hangs from the lowest point.
  2. **Head radius in profile.** 0.75 × the ear distance goes to zero when the head turns to profile and the ears overlap. The radius is now at least `TURNED_HEAD_RADIUS = 0.85` × the distance from the nose to the farther visible ear (when the nose is visible). The coefficient comes from a head model: ears about 14.5 cm apart, the nose tip about 11.5 cm in front of the ear axis. Over every turn from frontal to profile, the radius then stays within 0.85–1.1 × the frontal radius (0.75 × the ear distance) in a test property; facing the camera, the ear rule is larger, so frontal figures and the `figure.jpg` fixture are unchanged. The nose fallback (an ear hidden) takes the same floor, and draws a head from the nose and the other ear when a shoulder is hidden too (profile poses often hide the far ear and the far shoulder); with no ear and a shoulder hidden there is still no head.
  3. **Head centre with one ear hidden (coordinator follow-up).** Centred on the nose, a profile head with the far ear hidden sat in front of the face, about half outside it. Head model, seen from above: ears 14.5 cm apart, the eye centres 6.3 cm apart, the nose tip 11.5 cm in front of the ear axis, the cranium centred between the ears. Turned by yaw *t*, the visible (near) ear is 7.25 cos *t* from the cranium centre and the nose 11.5 sin *t* + 7.25 cos *t* from that ear, while the eyes are 6.3 cos *t* apart; so the cranium centre lies on the ear–nose segment at the fraction *w* = (7.25 / 6.3) × eye distance ÷ ear–nose distance from the ear: 1 (the nose) facing the camera, 0 (the ear) in strict profile, scale-free. *w* is 0 when an eye is hidden (an ear and an eye hidden means a turned head), then clamped to [1 − r/d, 1] (*d* the ear–nose distance), so the circle contains the nose, and the radius is raised to at least *w d*, so it contains the visible ear. In strict profile the nose is on the circle's edge and the centre 0.15 *d* in front of the ear. Facing the camera the head stays on the nose and the radius grows to reach the visible ear: only within about 6° of frontal, and by at most 0.15 *d* (a head with an ear and a shoulder hidden: 0.85 *d* → *d*). The reviewer chose this over keeping the radius and moving the centre 0.15 *d* off the nose towards the ear, which put a frontal face off-centre. A head whose radius would be 0 (an ear on the nose, a shoulder hidden) is not drawn. `figure.jpg` with every landmark visible is unchanged (the ear rule).

- **D3 (reviewer, 2026-10-09), guides in the page model.** Contract changes, all reflected above:
  1. **`tileLinesFor` takes `Pick<ImageDescriptor, 'pxW' | 'pxH' | 'edits' | 'lines'>`** instead of a full `ImageDescriptor`. Every descriptor fits, and test and E2E callers pass a minimal object; those four fields are all the mapping and the guide builders read.
  2. **The pipeline's guide input is optional.** `schedule(setup, images, guides?)` with the exported `GuidesOf`; without it the page models carry no guides, so callers that predate E2 are unchanged. The layout memo key does not include it.
  3. **The per-tile bound holds by construction.** `MAX_LINE_CMDS_PER_TILE + MAX_EDGE_VERTICES + MAX_FACES × MAX_CMDS_PER_FACE + MAX_POSES × MAX_CMDS_PER_POSE` = 200 + 4000 + 640 + 640 = 5480 ≤ 6000, pinned by a unit test, so raising any cap fails the build until the bound is revisited. The worst case built from the fixtures gives 4782 commands. If the bound were ever exceeded at runtime, nothing truncates: both renderers draw every command (pinned in `compose.lines.test.ts` and `preview.test.ts`); only memory and PDF size grow.
  4. **Page-model memory is recorded, not unit-tested** (see "Memory budgets"). In Chromium the worst case is 18.2 MB of 25. Sharing guide paths across study versions is not possible without a renderer change: the paths are in page mm and every tile sits elsewhere on the page, so it would need a per-tile translation in both renderers, which the "preview = PDF" rule forbids for guides.

- **Guides memory (2026-10-10), release on drain.** The memory test M3 with guides (E4) failed two budgets on macOS mobile-chromium: preview with guides 1553–1559 MB (< 1500) and settled after guides +184–190 MB (≤ +100). Contract changes, reflected in M4-R6, the D2 re-prepare note and "Memory budgets":
  1. **The scheduler releases each engine as soon as its queue drains.** When the landmark queue is empty and no landmark job runs, the scheduler closes the landmark engine (its worker terminates) and drops the runtime and model bytes it held; when the edge queue drains it closes the edge engine. The next job reads the bytes from the loader again (Cache Storage, verified: 16–105 ms in C3) and starts a new worker (landmarker creation 53–210 ms in C1). Within one run of queued jobs nothing changes: the engine stays loaded and is prepared again before every job with the same bytes (D2), and M4-R5a's one-landmarker-at-a-time order is unchanged. The engine's own 30 s idle release (`LANDMARK_IDLE_MS`) stays as a backstop for any other caller.
  2. **Why.** With the 30 s idle release, the landmark worker and the page's copy of the bytes were still alive when the user moved to Preview within 30 s, so the preview's own growth (about +150 MB of renderer RSS) stacked on the worker's. Measured at the "guides done" checkpoint (macOS): 1402–1408 MB before, 1227–1248 MB after; page ArrayBuffers at the settled checkpoint 15 MB before (the held runtime and model bytes), 1 MB after. Closing the idle edge worker as well lowered the preview phase by a further ~30 MB (1412–1425 → 1378–1399 MB, three runs each).
  3. **The macOS "settled after guides" excess is not live memory.** `footprint` on the renderer (macOS) at the settled checkpoints: dirty 756 MB before guides and 750 MB after, while its reclaimable pages (freed by the allocator, kept resident until memory pressure) grew from 45 to 194 MB; RSS counts them. In runs where macOS reclaimed them before the phase, the phase read 715–1158 MB. Linux returns them: on CI the settled phase is 1171–1178 MB against 1192–1223 MB before guides. The browser process keeps about +27 MB after guides on both systems: Playwright's ephemeral context keeps Cache Storage in memory, which holds the runtime and the models (on a device it is on disk).
  4. **Evaluated and not adopted.** Shrinking the page-side detection canvas to 0 × 0 after `transferToImageBitmap` changed nothing measurable (guides 1461–1493 MB vs 1467–1485, preview 1386–1404 vs 1378–1399). The detection bitmaps are already transferred to the worker and closed on every path there (C4 verified again: `landmark-api.ts` closes in `finally`, the engine closes on a rejection). The C3 in-memory fallback (no Cache Storage, or a failed `put`) still keeps its one copy of each asset: it is the only copy, and dropping it would mean downloading again without a click (M4-R19).
  5. **Measured (memory test M3, mobile-chromium, MB; before → after).** CI (ubuntu, three runs each): guides 1337–1356 → 1360–1400; preview with guides 1447–1494 → 1281–1308; settled after guides minus settled after studies −1 to −3 → −19 to −46; export 1329–1348 → 1323–1348. All budgets met before and after on CI; the preview margin grows from 6–53 MB to 192–219 MB. macOS (local, six isolated runs after): preview 1378–1399 (passes); settled +166 to +177 in five runs and −446 in one where macOS reclaimed first (fails, item 3); guides 1465–1485 (passes with 15–35 MB of margin, as before: 1452–1494); export 1510–1536 in five runs. In the full local E2E run (all projects, `CI=1`, three attempts) the guides phase read 1482, 1511 and 1526 MB: on macOS that phase sits at its budget with or without this change (1452–1494 MB in isolated runs before it); the CI run is the gate.
