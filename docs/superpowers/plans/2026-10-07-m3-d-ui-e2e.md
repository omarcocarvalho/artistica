# M3-D: Lines UI, Shell & E2E Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the Lines panel and its two new form primitives (D1), wire it into the desktop Settings tabs and the phone Studies step with remembered defaults and a page description that names the lines (D2), and prove the milestone end to end: the exit criterion and the desktop flows (D3), the phone flow, touch sizes, memory and timing (D4).

**Architecture:** `LinesPanel` reads and writes the images store only (like `StudiesPanel`). The shell decides where it lives: a third desktop tab and a collapsible section inside the phone Studies step (D1 decision). `LineDefaultsEffect` connects the images store's `appliedLines` and the selected image's line edits to the settings store's `lineDefaults`. Lines need no pipeline or preview wiring: they travel in the page model (C1) and both renderers draw them (C2, C3).

**Tech Stack:** React 19, Radix (Switch, RadioGroup via `SegmentedControl`), Tailwind v4, i18next, Testing Library, Playwright (+ axe), fast-check. No new dependencies.

**Spec:** `docs/spec.md` §2.7, §2.12, §3, §7, §8 M3 exit criterion **and** `docs/superpowers/plans/2026-10-07-m3-overview.md` (M3-R4, R9, R19, R20; Shared contracts → UI; Memory and Performance budgets; Testing strategy → E2E; owner Q6–Q12 defaults). **Design:** `design/lines.html` (Lines tab: "Composition" and "Line style" sections; the "Guides from the photo" section is M4 and is not built), `design/mobile-flow.html` (the `<details>` "Lines · 2 on" card in the Studies step), `design/mockup.css` (`.color-input`, `.input-pair`, `.seg`).

- [ ] **Step 5: `e2e/lines.spec.ts`** (all three desktop browsers):

**L-X1 exit criterion — the lines in the PDF match the preview exactly and stay sharp.**

1. Upload `flatGrey`, A4, mm. Lines tab: every type on, grid 4 × 5, spiral Top right, colour `#1f3fbf`, thickness 1.5 mm, opacity 100%. Wait for the preview to settle.
2. Export (`Create PDF` → download) → `pdfOn`. Switch every line off, export again → `pdfOff`.
3. **Vector, not pixels:** `pdfOn` and `pdfOff` have the same number of image XObjects with byte-identical data (`drawnImageData`), so no line is in the pixels; `pdfOn` has exactly 2 line strokes (solid, dashed) on the tile, `pdfOff` none; crop-mark counts are equal.
4. **Geometry:** for the drawn tile, take the trim from the image draw box (bleed off) and compute `tileLinesFor(settings, trim, turned, 0)` in node (import the pure code, as the specs already import the inspector; `turned` from the box aspect vs the image aspect). Each PDF stroke's path (in mm) equals the model's commands within 0.01 mm; colour within 1/255; width 1.5 mm in pt within 0.01 pt; clip = trim; dash = `centreDashMm(1.5)` for the second stroke.
5. **Preview = PDF:** map each PDF segment and curve (curves sampled at t = 0.25, 0.5, 0.75 with the Bézier formula) to sheet device pixels with `sheetScale`. For sample points at least 3 mm from any other subpath (computed from the same geometry), the sheet pixel is within RGB distance 60 of `#1f3fbf`; for points offset 2.5 mm perpendicular on either side and at least 2 mm from every subpath, it is within 30 of (170, 170, 170). At least 40 on-line and 40 off-line samples must qualify (assert the counts, so the test can't pass vacuously). Skip dashed-line samples that fall in a gap (use the dash phase from the start of the subpath).
6. Repeat 1–5 with **Original + Blurred + Values** on the photo: 3 tiles, each with its own clip and the same frame geometry.
