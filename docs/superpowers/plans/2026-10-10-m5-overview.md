## Rulings made in this plan (technical, not product)

Each ruling is binding for the sub-plans. Rulings marked "(owner Qn, default)" implement a recommended default and change only if the owner answers otherwise at the v1.0.0 sign-off.

**General**

- **M5-R1 No new dependencies.** Dragging uses Pointer Events and CSS transforms; presets use Zod, `Blob`, `<a download>` and `File.text()`; the near-viewport check uses `IntersectionObserver`. `package.json` and the lockfile do not change in M5. A task that finds it needs a package stops and asks the controller, who brings it to the owner (a new dependency is a 1.0 risk).

**Presets (A)**

- **M5-R2 What a preset holds (owner Q1, default).** `name`, `pageSetup` (all of `PageSetup`), `study` (all of `StudySettings`, versions included) and `lines` (all of `LineSettings` with `edges.on`, `face` and `pose` forced off; `edges.detailPct` kept). Never: unit, theme, language (device preferences), photos, names, content hashes, edits, crops, copies, sizes, layouts, manual arrangements, detections. The schema is a whitelist: unknown keys are dropped on save, load and import.
- **M5-R3 Where presets live.** A v5 field of the settings envelope, `presets: Preset[]`, in `artistica:settings`. At most `MAX_PRESETS` = 20; names 1–`MAX_PRESET_NAME` = 40 code points after trimming and collapsing whitespace, unique case-insensitively. A preset serialises to well under 1 KB, so 20 stay under 20 KB of the browser's ~5 MB `localStorage`. Migration v4 → v5 is the existing funnel: `parseSettings` fills `presets: []`. Saving an identical list does not write storage (M3 B2 rule).
- **M5-R4 The preset file.** `{ "format": "artistica-presets", "version": 1, "presets": [...] }`, UTF-8, pretty-printed, named `artistica-presets-YYYY-MM-DD.json` (local date). `PRESET_FILE_VERSION` = 1, independent of the settings version. Reading: size ≤ `MAX_PRESET_FILE_BYTES` = 64 KiB (checked on `File.size` before reading and on the text's UTF-8 length before `JSON.parse`), then `format`, then `version` (a newer version is refused with its own message; older versions pass through `PRESET_FILE_MIGRATIONS`, empty in v1), then at most `MAX_PRESETS_PER_FILE` = 50 presets, each parsed alone (a preset whose shape is wrong is skipped; a value out of range is sanitised and counted). `__proto__`, `constructor` and `prototype` keys are ignored. Errors: `too-large`, `not-json`, `not-presets`, `newer-version`, `empty`.
- **M5-R5 Import is local and total.** The file is read with `File.text()` from a file input that is separate from the photo dropzone; nothing is fetched; parsing never throws into the UI; one sanitizer per value (`normalizePageSetup`, `sanitizeStudy`, `sanitizeLines`), shared with settings.
- **M5-R6 Applying a preset (owner Q2, default).** In order: the page setup; the remembered study and line defaults (normalised as today: no versions, no line types); the images store's **session defaults** with the preset's full study (versions included) and lines (types included, guides off), so photos added later in this tab start with them; then "Apply to all" for studies and lines when photos are loaded. Refused while a photo is importing (M2-2). Asks first when photos are loaded. The session default ends when the study or line defaults change another way, or on reload. `StudyDefaultsEffect`/`LineDefaultsEffect` must not overwrite a session default in the same update (A2 test).

**Manual layout (B)**

- **M5-R7 Manual layout is session state keyed by photo copy.** `ManualLayout` lives in memory only (the arrange store), keyed by `blockId = ${imageId}#${copy}`. Layout item keys can change when studies or lines change (`occurrence` ranking); image ids can't, and both are session-scoped anyway. It is never persisted, never in a preset, never in a file.
- **M5-R8 Layered over the auto layout.** `computeLayout(setup, items, manual?)`: with no manual layout (null or absent) it is the M1–M4 engine and gives deep-equal results (golden snapshot unchanged). The first edit starts from `manualFromLayout(current result)`, so arranging starts from exactly what is shown. With a manual layout the result is a function of `(setup, items, manual)` only, and is deterministic in any input order.
- **M5-R9 One validity rule.** A block is valid when its trim box is inside the content box, its gutter-inflated box (right and bottom, as `packPages`) is disjoint from every other block's on that page, and, for an auto-sized photo, its tile short side is ≥ the smaller of `MIN_MANUAL_SHORT_MM` = 20 mm and the tile short side at the largest size the block fits the content box with (B1 ruling). A fixed-size photo has no manual minimum. The packer and the manual operations share this rule, so they can't disagree. Crop marks need no rule of their own: `cropMarksForTiles` already shortens or drops them near any neighbour.
- **M5-R10 Moving.** Pointer: the ghost follows the pointer in mm; pointer up commits; an edge within 2 mm of a content-box edge or of a neighbour's edge plus the gutter snaps to it. Keyboard: Arrow keys move 1 mm, stopping at the last valid position, flush with a margin or a gutter from the first photo in the way even when that is less than 1 mm (never jumping over a photo). Dropped over another page's sheet (desktop): that page. An invalid drop returns the block and says why.
- **M5-R11 Swapping.** Dropping a block onto another (the ghost covering the target's centre), Enter to pick up then Enter on another block, or "Swap with…": each block takes the other's box, fitted inside it at the larger of its two turns (ties keep the current turn), anchored at the box's top-left. A fixed-size block keeps its size, and the swap is refused when it doesn't fit the other box.
- **M5-R12 Resizing (owner Q8, Q9, defaults).** The aspect is kept; the corner opposite the handle stays put (keyboard: Shift + arrows, top-left fixed, 1 mm of tile width per step, as the crop editor); clamped to the minimum and to the largest valid size. It may go past the 300 DPI limit: the tile then carries `low-dpi` and the usual warning, as a fixed size does. Fixed-size photos are not resized on the page (no handles; "Fixed size: change it in Edit."); they can be moved and swapped.
- **M5-R13 Another page.** "Move to page" places the block at its current size where `findSpot(…, 'bssf', 'free')` finds room on that page, or on a new last page; refused when it doesn't fit. On the phone this is the only way across pages (the carousel's other pages are off screen).
- **M5-R14 Reconciling edits with changes (owner Q6, default).** The engine reconciles the manual layout with the current photos and settings on every run:

  | Change | What happens to the arrangement |
  |---|---|
  | photo or copy added | packed around the arranged blocks: existing pages first, then new pages; size from the auto search for the new items, scaled down to fit free space, not below the minimum; arranged blocks don't move |
  | photo or copy removed | its block goes; the gap stays |
  | crop, rotation or study versions change a block's shape | refitted inside its old box (top-left anchored, larger turn) |
  | fixed size changed | new size at the same corner if valid, else packed again |
  | lines, guides, study values, style | nothing (no shape change) |
  | paper, custom size or orientation | arrangement dropped; automatic layout; notice "The paper changed, so the photos were arranged automatically again." |
  | safe area, gutter, crop marks, bleed | kept if every block is still valid, else dropped with the notice "Your arrangement no longer fits the new margins, so the photos were arranged automatically again." |
  | Remove all, or the last photo removed | dropped, no notice |
  | Re-run auto layout | dropped after the confirmation "Re-run auto layout? Your moves and size changes will be lost." |

  The outcome is returned as `LayoutResult.manual` (`kept`, `adjusted` or `dropped` with a reason); for `kept` and `adjusted` its manual layout is `manualFromLayout(result)` and becomes the store's state.
- **M5-R15 An explicit Arrange mode.** Outside it the preview behaves exactly as in M4 (tap or click selects). In it, each block is one focusable `role="button"` with `aria-roledescription="movable photo"`, and `touch-action: none` applies to blocks and handles only, so pages can still be scrolled from the gaps. Handles: 24 × 24 px hit areas on desktop, 44 × 44 px on coarse pointers.
- **M5-R16 Pages follow the blocks.** Empty pages are removed and pages renumbered after every operation; the orientation and page size stay those of the arrangement (one orientation for all pages, as in `LayoutResult`).
- **M5-R17 Undo (owner Q7, default).** Up to `MAX_UNDO` = 50 arrange operations can be undone in this tab ("Undo" in the toolbar, also Ctrl/Cmd + Z while focus is in the preview); no redo; re-run, Remove all and a dropped arrangement clear it; engine adjustments (M5-R14) are not undo steps.
- **M5-R18 Preview = PDF.** The manual path produces an ordinary `LayoutResult`; `buildPageModels` and both renderers are unchanged. A renderer change for manual layout is a review blocker.
- **M5-R19 Drags are cheap.** No pipeline run, layout call or canvas redraw during a drag (the ghost is a CSS transform); one pipeline run at pointer up. The manual operations run on the main thread (validity only, no search); reconciliation runs in the layout worker with the rest of `computeLayout`.

**Accessibility, polish and performance (C, D, E)**

- **M5-R20 Centre dash (M3-2).** `centreDashMm(widthMm, tileShortMm)`: M3's `[max(1.5, 6w), max(1, 4w)]` when its period is at most a third of the tile's short side; else scaled down (6 : 4 kept) to that period, never below a period of `max(2.5, 2.5w)` mm. Unchanged for every tile whose short side is ≥ 30 × the width, so existing snapshots stay.
- **M5-R21 Pages near the view.** A page within one viewport of the scroller's visible area (vertical on desktop, horizontal in the phone carousel), the first page, and the page holding the selected photo want their study tiles and keep their canvases; other pages call `want(consumer, [])`, release the sheet canvas and their tile cache, and keep their size, buttons and page description. Without `IntersectionObserver` every page counts as near. Export is unaffected (it renders its own tiles).
- **M5-R22 Study worker timeout.** `STUDY_JOB_TIMEOUT_MS` = 20 s from the job's start (worker start-up included): terminate the worker and retry the job once on a fresh worker; a second timeout of the same job moves the preview to the main thread for the session. The queue always moves on.
- **M5-R23 Intake bounds.** A finished download keeps its fetch slot until a decode slot is free, so at most `FETCH_CONCURRENCY + DECODE_CONCURRENCY` fetched blobs wait in memory; the CORS probe listens to the import's signal as well as its timeout; `cancelImports()` aborts pending imports without removing loaded photos (owner Q-H5, default).
- **M5-R24 "Updating layout…" only when slow.** The preview's status region speaks after the layout has been computing for `UPDATING_ANNOUNCE_DELAY_MS` = 500 ms, then says "Layout updated." at the end; faster updates are silent (the panel that caused them announces its own result). `aria-busy` stays immediate.
- **M5-R25 Indeterminate progress under reduced motion** fills the whole track with a static stripe pattern, never a partial width.
- **M5-R26 Segmented controls** follow the ARIA radio-group pattern: all four arrows move and select (wrapping; Left and Right swapped in RTL), and Home/End select the first/last enabled option.
- **M5-R27 How performance is measured.** `performance.mark`/`measure` named `artistica:*` around the layout call, the page models and each page's draw; local to the page, never sent or stored. "A preview update" (spec §3) is the time from the input event to the last visible page's redraw of geometry and lines; study tiles that render afterwards are recorded separately with their existing bound (owner Q11, default). Timings assert on CI chromium and are recorded, with the run id, in the M5 ledger.

## Determinism

- **Auto layout:** unchanged. `computeLayout(setup, items)` and `computeLayout(setup, items, null)` are deep-equal to M4's; `golden.test.ts` and its snapshot don't change (B2).
- **Manual layout:** the result is a pure function of `(setup, items, manual)`; operations are pure; reconciliation uses the engine's own deterministic search; placements are sorted as `assemble` sorts them. Property tests check order independence (B2) and E2E B-D1 checks byte-identical PDFs from the same script.
- **Presets:** `buildPresetFile` is deterministic (stable key order, fixed indent); a round trip is exact (A1).
- **Centre dash:** a pure function of width and tile size, in the page model only (E2).

## Contract change requests

### Ruled

**A1 (presets model, PR #155).**
- `src/shared/model/preset.ts` holds its own copy of the page-setup Zod schema (the ranges of `features/settings/schema.ts`), because `preset.ts` can't import `features/settings` without a cycle once A2 makes the settings schema import `preset.ts`. **Binding for A2:** leave only one copy. Either `settings/schema.ts` imports the schema from `preset.ts`, or the schema moves to `src/shared/model/` and both import it. A property test keeps the two copies equal until then.
- `presetFromSettings` keeps a name that `presetName()` refuses as given (the contract comment says `presetName()` is applied), so `savePreset` can return `'bad-name'`. `sanitizePreset` returns `null` for such a name, so on import the preset is skipped and counted (Q13, accepted default in the M5 ledger), and `buildPresetFile` leaves it out.

**B1 (manual layout model, PR #156).**
1. M5-R9's minimum: for an auto-sized photo the tile short side must be ≥ min(20 mm, the tile short side at the largest size the block fits the content box with); a fixed-size photo has no manual minimum. "The content box's short side" only covered a single tile: four 1:1 study versions on A6 fit at most 16.75 mm per tile, and a fixed size can be 10 mm (`MIN_FIXED_MM`). With the extension, every valid auto layout converts to a valid manual one.
2. M5-R10 keyboard moves stop flush against the obstacle or margin in the way, not on the last whole millimetre. Otherwise a block at a fractional auto-layout position could never reach the margin or its neighbour. `nudge` still rounds `dx` and `dy` to whole millimetres and never jumps over a photo.
3. An unknown block id, a block whose photo is missing from `items`, and a self-swap throw `RangeError`; they are programming errors, not refusals. **Binding on B3 and B4:** drop a selection or a picked-up block whose block id is not in the reconciled manual layout before calling an operation.
4. Refusal reasons beyond the plan: a page that does not exist is `outside` (`moveBlock`, and `moveToPage` with `page > pageCount`); a resize to the current width is `blocked`, or `min` when a smaller width was asked for; a non-positive or NaN width clamps to the minimum; an infinite width grows as far as is valid; a swap that would put an auto photo under its minimum is `does-not-fit`. `moveToPage` to the block's own page re-places it at the `findSpot` spot.
5. `blockIdOf` takes `Pick<LayoutItemInput, 'key' | 'imageId'>` (wider, compatible), so it also works on a `Placement`. `fitUnturned` is exported from `geometry.ts`.

## Questions for the owner

> **How to answer:** each question has a recommended default, and the plans build it, marked "(owner Qn, default)" in the sub-plans. Under the owner's delegation of 2026-10-10 the controller accepted every default, so M5 needs no answer to proceed. Answer "ok" at the v1.0.0 sign-off to keep a default, or write your own answer after **A:** to change it (a change becomes M6 work).

### New questions raised by M5

Q1. **What a preset holds.** The spec's example is "A4 value studies".
   _Recommendation:_ a preset holds the **page setup** (paper, orientation, safe area, gutter, crop marks, bleed), the **study settings** (versions, blur, values, hue) and the **line settings** (which lines, grid size, spiral corner, colour, thickness, opacity, edge Detail). It doesn't hold the unit, theme or language (those belong to the device), and never anything from a photo. It never switches on edge, face or pose guides, so applying a preset can never start a download (M4 Q10).
   **A:** accepted (recommended default), controller under the owner's delegation, 2026-10-10.

Q2. **What applying a preset does.**
   _Recommendation:_ it sets the page setup at once, applies the preset's studies and lines to every photo already loaded (after asking, when there are photos), and photos you add afterwards in the same tab start with them too, versions and lines included, so "apply a preset, then add photos" works. The remembered defaults follow today's rules (study values and line style are remembered, versions and line types are not), so after a reload new photos start with Original only and no lines, as now. Not allowed while photos are still importing.
   **A:** accepted (recommended default), controller under the owner's delegation, 2026-10-10.

Q3. **Where presets live in the app.**
   _Recommendation:_ a **"Presets"** button in the top bar (desktop and phone) opens a dialog (a bottom sheet on the phone) to save the current settings under a name, apply, rename, delete, export all and import. No built-in starter presets: the list starts empty with a short hint.
   **A:** accepted (recommended default), controller under the owner's delegation, 2026-10-10.

Q4. **Limits and name clashes.**
   _Recommendation:_ up to **20 presets** on a device; names up to 40 characters, unique ignoring case. Saving under a taken name asks "Replace it?". "Export all" writes one file, `artistica-presets-2026-10-10.json`. Importing adds the file's presets and renames clashes ("A4" → "A4 (2)"); files over 64 KB, files from a newer version of Artistica, and broken files are refused with a clear message.
   **A:** accepted (recommended default), controller under the owner's delegation, 2026-10-10.

Q5. **How arranging works.**
   _Recommendation:_ an **Arrange** button on the preview turns on arranging (so tapping a photo still just selects it the rest of the time, and scrolling on a phone doesn't move photos by accident). A photo moves with all its study versions as one block. Drag to move (also to another page on desktop), drop onto another photo to swap the two, drag a corner to resize (the shape is kept). Photos keep at least 20 mm on their short side and stay inside the margins and a gutter apart. From the keyboard: arrow keys move by 1 mm, Shift + arrows resize, Enter swaps; and every action also has buttons ("Move to page", "Swap with…", "Width"), so nothing needs a drag.
   **A:** accepted (recommended default), controller under the owner's delegation, 2026-10-10.

Q6. **What happens to an arrangement when things change.**
   _Recommendation:_ added photos fill free space (then new pages) without moving arranged ones; a removed photo leaves a gap; a photo whose shape changes (crop, rotation, study versions) is refitted in its space; a new paper size or orientation, or margins the arrangement no longer fits, go back to automatic layout with a short notice; line and study-value changes don't touch it. **Re-run auto layout** asks "Your moves and size changes will be lost." before it goes back.
   **A:** accepted (recommended default), controller under the owner's delegation, 2026-10-10.

Q7. **Undo.**
   _Recommendation:_ an **Undo** button (and Ctrl/Cmd + Z) for the last 50 arranging actions in this tab; no redo. Arrangements are never saved: reloading the page (which clears the photos too) starts over.
   **A:** accepted (recommended default), controller under the owner's delegation, 2026-10-10.

Q8. **Photos with a fixed size.**
   _Recommendation:_ they can be moved and swapped but not resized on the page (their size is set in Edit); a swap that would need a different size is refused with a message.
   **A:** accepted (recommended default), controller under the owner's delegation, 2026-10-10.

Q9. **Resizing past what the photo's pixels allow.**
   _Recommendation:_ allowed, with the usual low-resolution warning on the photo (as with a fixed size), because sometimes a bigger, softer reference is what you want. The automatic layout still never goes past 300 DPI.
   **A:** accepted (recommended default), controller under the owner's delegation, 2026-10-10.

Q10. **The logo** (review round 1, D11: "a proper logo pass in M5").

   **A:** accepted (recommended default), controller under the owner's delegation, 2026-10-10.

Q11. **What "the preview updates in under 200 ms" means** (spec §3).

Blurred and value tiles may finish shortly after (they are computed in the background, about 1 s for 20 photos), and are measured separately. A missed target is fixed, not relaxed.
